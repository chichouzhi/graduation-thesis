## 整体汇报主线

本次答辩建议围绕一条清晰主线展开：

传统毕业设计管理系统主要解决流程记录问题，但在选题阶段仍存在学生不了解课题要求、教师缺少学生能力依据、推荐结果不可解释、选题后过程衔接不足等问题。本文设计并实现了一个融合大模型辅助、学生画像、课题画像、可解释推荐和异步任务机制的毕业设计选题双向选择系统，使选题流程从“人工浏览和判断”扩展为“画像匹配、解释推荐、人工确认、过程跟踪”的闭环。

汇报重点建议：

1. 为什么要做：毕业设计选题存在信息不对称和匹配依据不足。
2. 做了什么：实现面向学生、教师、管理员的选题双向选择系统。
3. 怎么做的：前后端分离架构、画像建模、Top-N 可解释推荐、Redis 队列与 Worker 异步任务。
4. 效果如何：后端 82 项测试通过，前端 61 项测试通过，推荐解释和异常处理能够按设计运行。
5. 创新在哪里：把画像化可解释推荐与大模型辅助能力嵌入完整选题业务流程，同时保留人工决策边界。

6-8 分钟答辩时，不建议逐页展开所有实现细节。主线应控制为“背景问题 1 分钟、系统设计 2 分钟、核心实现 2 分钟、测试与总结 2 分钟”。数据库、前端页面和对比分析只保留关键句，详细内容可作为老师追问时的备用材料。

## 第 3 页 研究背景

### 页面标题

毕业设计选题是毕业设计全过程的起点

### 页面正文

- 毕业设计通常包含选题、调研、方案设计、系统实现、测试验证和论文撰写等阶段。
- 选题匹配程度会影响学生后续调研质量、系统开发投入和论文完成效果。
- 传统毕业设计管理系统已能支持课题发布、志愿记录、材料提交和过程归档。
- 但“流程线上化”并不等同于“选题匹配合理化”。

### 建议视觉

展示“选题 -> 调研 -> 开发 -> 测试 -> 论文”的流程图，将“选题”作为高亮起点。

### 讲述重点

毕业设计选题不是简单选择一个题目，而是学生兴趣、技术基础、教师方向、课题要求和指导容量之间的综合匹配。选题阶段一旦匹配不充分，后续调研、开发和论文写作都会受到影响。

## 第 4 页 问题分析

### 页面标题

## 第 7 页 系统总体架构

### 页面标题

前后端分离 + 异步任务处理的总体架构

### 页面正文

- 前端：React、TypeScript、Vite，负责页面展示、表单交互和状态反馈。
- 后端：Flask、SQLAlchemy，提供 RESTful API、权限校验和业务服务。
- 数据库：PostgreSQL，保存用户、学期、课题、志愿、指导关系、文档任务和对话消息。
- 队列：Redis，承载 chat_jobs、pdf_parse、document_jobs、keyword_jobs、reconcile_jobs。
- Worker：处理画像生成、PDF 解析、文档摘要、对话回复和指导关系对账。
- 外部能力：大模型、PDF 解析、NLP 和存储等通过 adapter 层统一封装。

### 建议视觉

直接使用论文图 3-2“系统总体架构图”，并在 PPT 中用颜色标出“同步 API 链路”和“异步 Worker 链路”。

### 讲述重点

系统采用前后端分离架构。普通请求由前端访问 Flask API，再读写 PostgreSQL。对于大模型调用、PDF 解析等耗时任务，API 只负责受理和入队，具体处理交给 Worker 完成，从而避免阻塞 HTTP 请求。

## 第 8 页 后端分层设计

### 页面标题

后端分层保证业务边界清晰

### 页面正文

- API 层：解析 HTTP 请求，返回统一响应。
- Service 层：处理权限、业务规则、事务和入队决策。
- use_cases 层：组织对话、文档处理、画像生成等任务流程。
- task 层：负责队列入队、任务消费和状态回写。
- adapter 层：封装大模型、PDF、NLP、Storage 等外部能力。
- model 层：维护 ORM 实体和数据库持久化。

### 建议视觉

### 讲述重点

## 第 9 页 选题主流程设计

### 页面标题

从课题发布到指导关系建立的业务闭环

### 讲述重点

推荐结果不会直接替代师生决策，而是作为辅助依据进入双向选择流程。最终仍由学生提交志愿、教师确认录取，系统再建立指导关系，保证业务规则和人工决策边界。

## 第 11 页 画像生成机制

### 页面标题

学生画像与课题画像为推荐提供输入

### 页面正文

| 画像类型 | 输入内容 | 输出字段 | 作用 |
| --- | --- | --- | --- |
| 课题画像 | 题目、简介、技术要求、教师研究方向 | 关键词、难度、能力要求、适合学生、风险提示、摘要 | 描述课题要求 |
| 学生画像 | 兴趣方向、技能基础、项目经历、目标、投入时间 | 兴趣关键词、技能标签、目标倾向、潜在短板 | 描述学生能力与偏好 |

关键设计：

- 画像生成发生在课题创建、课题更新或学生维护画像阶段。
- 大模型辅助抽取关键词和整理要求。
- 推荐接口只读取已经生成的画像字段，不实时调用大模型。

### 建议视觉

做成左右两条输入输出链路：课题文本 -> 课题画像，学生描述 -> 学生画像，中间标出 LLM 辅助抽取。

### 讲述重点

画像是推荐计算的基础。本文把非结构化文本转化为可计算字段，并且将画像生成放在写路径或异步任务中完成。这样推荐接口可以保持稳定，不受外部模型实时响应影响。

## 第 12 页 智能推荐模块

### 页面标题

基于画像与规则约束的 Top-N 可解释推荐

### 页面正文

推荐输入：

- 学生画像：skills、keywords、interests、goal、weekly_available_hours。
- 课题画像：keywords、required_capabilities、difficulty_label、risks。
- 业务约束：课题状态、容量、已选人数、当前学期。

推荐计算：

- 关键词匹配：使用集合重合程度和 Jaccard 相似度。
- 技能匹配：比较学生技能与课题 required_capabilities。
- 难度适配：结合课题难度与学生能力、投入时间。
- 容量与状态约束：过滤未发布、关闭或容量不可用课题。
- 综合排序：返回 Top-N 推荐结果。

### 建议视觉

使用论文图 3-8“智能推荐计算流程图”，旁边放一条简化公式：综合得分 = 关键词匹配 + 技能匹配 + 难度适配 + 业务约束。

### 讲述重点

毕业设计选题数据通常以学期为单位，历史交互数据有限，因此本文没有采用复杂训练模型，而是使用画像与规则约束的推荐方式。这种方式更透明，也更容易向学生和教师解释推荐依据。

## 第 13 页 推荐解释设计

### 页面标题

推荐结果不仅给排序，还说明原因

### 页面正文

推荐结果解释字段：

- 匹配关键词：学生兴趣与课题关键词的共同词项。
- 匹配技能：学生技能与课题技术要求的对应关系。
- 匹配能力：与 required_capabilities 对应的能力说明。
- 难度适配：课题难度与学生投入时间、能力基础是否协调。
- 容量状态：课题是否仍有可选名额。
- 风险提示：技能不足、容量紧张、低匹配等潜在问题。

示例表达：

# 可能被问到的问题与回答提示

## 1. 为什么没有使用深度学习推荐模型？

毕业设计选题通常以学期为单位，课题数量和历史交互数据规模有限，不适合直接训练复杂推荐模型。本文采用基于画像和规则约束的 Top-N 推荐方法，主要考虑透明性、可解释性和工程落地性。后续如果积累真实选题数据，可以进一步引入语义向量、知识图谱或图神经网络推荐。

## 2. 大模型是否会直接决定学生选题？

不会。本文将大模型限定在关键词抽取、画像整理、文档摘要和对话辅助环节。推荐模块读取已生成画像进行只读计算，最终仍由学生提交志愿、教师接受或拒绝，系统只提供辅助依据，不替代师生决策。

## 3. 推荐结果如何解释？

系统返回匹配关键词、匹配技能、能力要求、难度适配、容量状态和风险提示等字段。学生可以看到系统为什么推荐某个课题，教师也可以把这些字段作为筛选志愿时的参考。

## 4. 为什么要使用异步任务？

大模型调用、PDF 解析和文档摘要耗时不稳定。如果在 HTTP 请求中同步等待，会影响接口响应和用户体验。本文使用 Redis 队列和 Worker 处理耗时任务，API 只负责受理、入队和返回任务标识，前端通过任务状态查询进度。

## 5. 系统如何保证测试可验证？

后端测试覆盖队列与 Worker、架构约束、应用工厂、Policy 策略、Worker 运行时和课题关键词处理，共 82 项通过。前端测试覆盖登录、仪表盘、课题页、任务看板、文档页、对话页和路由保护，共 61 项通过。此外，生产构建和系统联调均完成验证。
