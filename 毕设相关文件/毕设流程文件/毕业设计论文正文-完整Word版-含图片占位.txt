1 绪论

1.1 课题背景

毕业设计（论文）是本科教学体系中综合性最强的实践教学环节之一。对计算机类、软件工程类专业而言，毕业设计不仅要求学生能够综合运用程序设计、数据库、网络通信、软件工程、系统测试等课程知识，还要求学生能够围绕真实问题完成需求分析、系统设计、编码实现、部署运行和论文表达。因此，毕业设计过程既是学生专业能力的集中检验，也是高校教学管理质量的重要体现。

在毕业设计全过程中，选题与师生双向选择是后续研究和开发工作能否顺利开展的起点。传统选题方式通常由教师发布题目、学院审核题目、学生浏览题目并填报志愿、教师依据志愿和学生情况确认指导关系。该流程在形式上能够体现师生双向选择，但在实际运行中仍存在较明显的信息不对称问题。学生面对大量题目时，往往只能依据题目名称、简短简介和个人直觉判断是否适合自己，难以准确理解题目所需技术基础、预期工作量、潜在风险及与自身能力的匹配程度。教师在筛选学生时，也常常缺少结构化的学生兴趣、技能和投入时间信息，只能依赖成绩、课堂印象或简单沟通进行判断，导致匹配效率和匹配质量受到影响。

随着高校信息化建设的发展，许多毕业设计管理系统已经实现了课题申报、志愿填报、过程材料提交、成绩评定等环节的线上化。这类系统有效降低了纸质流转成本，提高了教务管理效率，但其主要定位仍是流程管理和数据记录。在选题双向选择这一关键环节中，传统系统通常能够记录“题目是否发布”“学生是否填报志愿”“教师是否确认”等状态，却难以进一步回答“某个题目需要什么能力”“某个学生适合哪些题目”“推荐依据是否可解释”“互选结果是否能继续支撑过程管理”等问题。也就是说，传统系统在流程信息化方面已有较成熟实践，但在选题匹配智能化、互选决策辅助化和后续过程支撑方面仍有提升空间。

近年来，大型语言模型和自然语言处理技术快速发展，在文本理解、摘要生成、问答对话、关键词提取和语义分析等方面表现出较强能力。将这些能力适度引入毕业设计选题场景，有助于把教师题目描述转化为题目画像，把学生兴趣、技能和投入时间转化为学生画像，并在此基础上形成可解释的选题推荐结果。基于此，本文围绕“智能化毕业设计选题双向选择系统的设计与实现”展开研究，设计并实现一个前后端分离的 Web 应用原型，面向学生、教师和管理员等角色，提供课题管理、题目画像、学生画像、智能推荐、志愿填报、教师决策、指导关系确认以及选题后文档辅助、问答辅助和进度看板等功能。

本系统并不试图替代学校已有教务管理体系，而是将重点放在“围绕毕业设计选题实现智能双向选择辅助”上。系统以课题库和互选流程为主线，通过题目画像和学生画像提升选题匹配的可解释性，通过志愿填报和教师决策完成师生双向选择，通过指导关系确认把选题结果落到后续过程管理；智能问答、文献处理和任务看板则作为选题后的辅助模块，为毕业设计的持续推进提供支撑。

1.2 研究意义

本课题具有较强的工程实践意义和应用探索价值。

首先，本课题有助于提升毕业设计选题阶段的信息透明度。系统将教师录入的题目描述转化为结构化题目画像，包括关键词、难度、能力要求、适合学生类型和风险提示等信息；同时允许学生维护个人画像，包括兴趣方向、已有技能、关键词、目标和每周可投入时间等信息。在此基础上，系统采用规则化、可解释的推荐方式输出候选课题，使学生不再完全依赖主观浏览，也使教师能够更清晰地理解学生与题目的匹配依据。

其次，本课题探索了人工智能能力在毕业设计管理场景中的边界化应用。与直接在推荐接口中调用大模型不同，本系统将大模型能力主要用于题目画像分析、智能问答和文档辅助等环节，而推荐结果则由可解释规则生成。这种设计既能够利用大模型对文本的理解能力，又避免将最终选择完全交给不可解释的生成式输出，有利于保证系统结果的可控性、可测试性和可答辩性。

再次，本课题体现了现代 Web 工程方法在毕业设计系统中的应用。系统采用 Flask 后端、React 前端、PostgreSQL 数据库、Redis 队列、Docker Compose 部署和自动化测试等技术，按照 API 层、Service 层、Use Cases 编排层、Task/Worker 层、Adapter 层和 Model 层进行分层设计。该架构能够降低模块耦合度，提高系统可维护性，并使聊天、文献处理、题目画像等耗时任务通过异步队列完成，避免阻塞 HTTP 请求。

最后，本课题对高校毕业设计选题系统建设具有参考意义。系统不是单纯的题目列表和志愿表单，而是围绕“教师录题、题目画像、学生画像、智能推荐、志愿提交、教师确认、指导关系形成”构建完整的智能双向选择流程；文档处理、智能问答和过程看板作为辅助模块，服务于选题结果落地后的毕业设计推进。该设计为传统毕业设计选题系统引入智能化辅助能力提供了一个轻量化、可演示、可扩展的实现样例。

1.3 国内外研究现状

毕业设计管理系统的研究主要集中在流程信息化、双向选择机制和智能辅助三个方向。

在流程信息化方面，较早的毕业设计管理通常依赖纸质材料和人工汇总，存在工作量大、状态追踪困难、材料归档不便等问题。随着 Web 技术发展，基于 B/S 架构的毕业设计管理系统逐渐成为主流。这类系统通常包括课题申报、题目审核、学生选题、过程材料提交、论文评阅和成绩管理等功能，能够明显提升教学管理效率。前后端分离架构进一步增强了系统的交互体验和可维护性，使前端页面与后端业务服务能够通过 RESTful API 解耦开发。

在双向选择机制方面，相关研究普遍认为毕业设计选题不是简单的资源分配问题，而是教师研究方向、题目要求、学生兴趣和学生能力之间的匹配问题。传统系统多通过志愿优先级、题目容量、教师确认等规则实现线上互选，但匹配逻辑大多基于结构化字段和人工判断。对于题目描述中的技术要求、学生个人偏好与能力之间的语义关联，传统系统缺乏深入分析能力。

在智能辅助方面，大型语言模型和自然语言处理技术为毕业设计支持系统提供了新的可能。大模型可以用于文献摘要、论文结构建议、代码问题解释、题目描述分析和关键词抽取等任务。但大模型也存在幻觉、结果不可完全解释、接口耗时较长、外部服务不可控等问题。因此，将 AI 能力引入教育系统时，应结合明确的业务边界、异步任务处理、提示词约束、结果校验和人工决策机制。本文设计的系统正是在上述背景下，将 AI 能力作为辅助工具嵌入选题和过程支持环节，而不是让 AI 直接替代师生判断。

1.4 本文主要研究内容

本文的主要研究内容包括以下几个方面。

第一，分析智能化毕业设计选题双向选择系统的业务需求。围绕学生、教师和管理员等角色，重点梳理课题发布、题目画像、学生画像、智能推荐、志愿填报、教师决策和指导关系确认等选题双向选择需求，同时分析任务看板、智能问答和文献处理等选题后辅助需求，并提出系统非功能需求。

第二，设计系统总体架构和数据模型。系统采用前后端分离的 B/S 架构，后端使用 Flask Application Factory 组织应用，按照 API、Service、Use Cases、Task/Worker、Adapter、Model 等层次进行分层；前端使用 React、TypeScript、Vite、React Router、TanStack Query、Zustand、Axios 和 Tailwind CSS 构建单页应用；数据库采用 PostgreSQL，队列采用 Redis，部署采用 Docker Compose。

第三，实现核心业务模块。系统实现登录认证、当前用户信息维护、学期与配置管理、课题创建与审核、题目画像生成、学生画像维护、推荐结果解释、志愿提交与处理、指导关系生成等双向选择核心功能，并实现里程碑任务管理、聊天会话、文档任务和异步 Worker 消费等辅助功能，形成以选题互选为中心的毕业设计支持闭环。

第四，开展系统测试与验证。通过后端 Pytest、架构约束测试、契约校验、前端 Vitest、构建检查和本地 Docker Compose 联调，验证系统主要功能、接口契约、分层约束和异步处理流程的正确性。

2 系统需求分析

2.1 可行性分析

从技术可行性看，本系统采用的 Flask、React、PostgreSQL、Redis、Docker Compose 等技术均为成熟开源技术，具有稳定的生态和丰富的工程实践。Flask 适合构建轻量级 RESTful API，React 和 TypeScript 适合实现复杂的前端交互，PostgreSQL 能够支撑关系型数据持久化，Redis 能够承担轻量级任务队列和状态缓存，Docker Compose 则便于在本地和演示环境中快速启动完整系统。系统所需的大模型能力通过 Adapter 层进行封装，既可对接真实 OpenAI-compatible HTTP 服务，也可在演示和测试环境中使用 mock provider，降低外部依赖对系统可运行性的影响。

从经济可行性看，系统主要依赖开源框架和本地容器化环境，不需要采购专用硬件。大模型接口采用可配置方式接入，在毕业设计原型阶段可以使用 mock 或低频调用方式完成验证，避免高额训练和推理成本。系统没有自行训练推荐模型，而是采用题目画像与学生画像的规则匹配策略，这种方案开发成本较低、实现周期可控，也更符合本科毕业设计对工程完整性和可解释性的要求。

从操作可行性看，系统面向学生和教师的业务流程与实际毕业设计选题流程一致。学生登录后维护个人画像、浏览题目、查看推荐解释并提交志愿；教师发布题目、查看题目画像、处理学生志愿并形成指导关系；管理员维护学期和审核题目。在指导关系形成后，学生和教师再使用聊天、文档和任务看板等辅助功能推进毕业设计过程。系统页面围绕选题核心流程组织，学习成本较低，适合答辩演示和小规模试用。

图 2-2 系统功能模块结构图


从任务书要求和系统标题出发，本系统功能分为两类：一类是围绕“智能化毕业设计选题双向选择”的核心功能，包括课题管理、题目画像、学生画像、智能推荐、志愿填报、教师决策和指导关系；另一类是围绕毕业设计选题结果落地的辅助功能，包括智能问答、文献处理和过程看板。论文后续设计与实现也以核心选题互选链路为主线展开。

2.3.1 身份认证与用户画像需求

系统应支持用户登录、令牌刷新、登出和当前用户信息查询。登录成功后，前端保存认证态，并在后续请求中携带访问令牌。系统应支持读取和更新当前用户信息，其中学生画像是推荐功能的重要输入。学生画像包括兴趣方向、技能、关键词、目标和每周投入时间等字段。通过结构化画像，系统能够更好地分析学生与题目的匹配关系。

2.3.2 学期与配置管理需求

毕业设计选题通常以学期或届次为单位组织。系统应支持学期列表、新建学期、学期详情、学期更新以及学期级 LLM 配置维护。学期信息用于约束题目、志愿、推荐、聊天和文档任务的业务范围，避免不同届次或不同批次的数据混用。

2.3.3 课题管理与题目画像需求

教师应能够创建、编辑、删除或撤回题目，并提交管理员审核。题目包括标题、简介、要求、容量、学期、教师等基本字段。题目创建或更新后，系统应触发题目画像生成流程，提取关键词、难度标签、难度原因、所需能力、适合学生类型、风险提示和总结说明等信息。题目画像应在题目详情和推荐接口中被使用，为学生理解题目和系统推荐提供依据。

2.3.4 智能推荐与可解释输出需求

系统应根据学生画像与题目画像生成 Top-N 推荐列表。推荐功能不直接调用大模型，而是基于已生成的题目画像和学生画像进行规则排序。推荐结果应包含分数和解释信息，例如匹配技能、匹配关键词、匹配能力、难度适配、容量状态、风险提示和推荐理由。可解释输出有助于学生理解推荐依据，也便于教师和答辩评审理解系统逻辑。

2.3.5 志愿填报与指导关系需求

学生应能够针对题目提交志愿，并设置第一或第二志愿。教师应能够查看某个题目的学生申请，并对申请进行接受或拒绝。教师接受申请后，系统应生成指导关系，并维护题目已选人数等派生数据。为保证数据一致性，志愿接受过程需要在事务中更新申请状态、指导关系和题目计数，并在事务提交后触发内部对账任务。

2.3.6 智能问答需求

系统应支持毕业设计场景下的智能问答。学生可以创建会话、发送消息、查看历史消息和异步任务状态。由于大模型生成可能耗时较长，系统不应在 HTTP 请求线程中同步等待完整回答，而应在接收用户消息后创建用户消息和 assistant 占位消息，写入 ChatJob 后入队，由 Worker 消费队列并回写 assistant 回复。

2.3.7 文献处理需求

学生在毕业设计过程中需要阅读大量论文、技术文档和外文资料。系统应支持上传 PDF 文献并创建文档处理任务，任务类型包括摘要、结论提取和对比分析等。上传请求返回任务受理结果，后台 Worker 负责 PDF 文本解析、分块处理、摘要生成和结果回写。前端通过轮询任务状态展示 pending、running、done 和 failed 等状态。

2.3.8 过程看板需求

系统应支持毕业设计里程碑管理。学生可以创建、更新和删除里程碑任务，记录任务标题、状态、时间范围等信息。教师在形成指导关系后，可以按学生查看其任务进度。过程看板有助于将选题结果延伸到毕业设计中后期的过程管理，避免系统只停留在选题阶段。

2.4 非功能需求分析

系统的非功能需求主要包括性能、可靠性、可维护性、安全性和可测试性。

在性能方面，聊天消息发送和文献上传等耗时任务应采用异步受理方式。API 层只负责校验、落库和入队，并在较短时间内返回 202 状态，避免因外部大模型接口耗时导致请求阻塞。推荐接口属于同步只读接口，应基于数据库中已有画像快速计算并返回结果。

在可靠性方面，系统应保证数据库写入与队列入队之间的一致性。对于需要异步处理的任务，应先提交数据库占位记录，再执行入队操作；若入队失败，应进行失败补偿，避免任务长期处于 pending 状态。Worker 处理任务时应能够记录 running、done、failed 等状态，并在异常情况下写入错误码和错误信息。

在可维护性方面，系统采用分层架构，API 层只处理 HTTP 边界，Service 层处理业务事务和入队决策，Use Cases 层负责 LLM 和文档任务编排，Task/Worker 层负责队列消费，Adapter 层隔离外部服务，Model 层负责数据持久化。通过 import-linter 和静态脚本约束模块依赖，避免路由层直接访问模型、任务或外部 Adapter。

在安全性方面，系统应对不同角色进行访问控制。学生、教师和管理员只能访问与其身份相符的数据和操作。接口错误应使用统一错误结构返回，不暴露敏感实现细节。Refresh Token 和访问令牌应有清晰的生命周期控制。

在可测试性方面，系统应提供后端单元测试、集成测试、契约测试、架构约束测试和前端组件测试。大模型接口应通过 Adapter 层和 mock provider 隔离，使测试环境不依赖真实外部服务。

3 系统总体设计

3.1 系统设计目标

本系统的设计目标是实现一个功能完整、结构清晰、可运行、可测试、可演示的智能化毕业设计选题双向选择系统原型。系统应满足以下目标：

第一，形成完整的选题双向选择业务闭环。系统需要覆盖教师题目发布、题目画像生成、学生画像维护、智能推荐、志愿提交、教师处理志愿和指导关系生成等环节，使选题流程不再只是题目列表浏览和人工确认，而是具备数据分析、匹配推荐和互选确认能力。

第二，体现选题场景下的智能化辅助能力。系统应将自然语言处理和大模型能力优先用于题目分析与画像生成，通过学生画像和题目画像完成可解释推荐；文档处理和问答辅助则服务于选题后的毕业设计开展，作为系统智能化能力的补充。

第三，保证工程结构可维护。系统应避免将所有逻辑堆叠在路由或页面组件中，而是通过后端分层和前端模块化实现职责拆分。核心异步任务应通过队列和 Worker 完成，保证 API 响应稳定。

第四，便于部署和演示。系统应支持 Docker Compose 一键启动后端依赖服务，并通过 Vite 启动前端开发环境。演示环境应包含学生、教师和管理员账号，能够按照答辩演示链路完成操作。

3.2 系统技术架构

【图片占位：图 3-1 系统总体架构图。建议展示浏览器前端、Vite 代理、Flask API、PostgreSQL、Redis、Worker、LLM Adapter、PDF Adapter、NLP Adapter 和 Storage Adapter 之间的关系。】
图 3-1 系统总体架构图


系统采用前后端分离的 B/S 架构。前端运行在浏览器中，通过 HTTP 调用后端 RESTful API；后端运行 Flask API 服务，负责身份认证、业务处理、数据持久化和任务入队；PostgreSQL 负责业务数据存储；Redis 负责队列 broker 和部分状态能力；Worker 进程消费 Redis 队列并执行聊天生成、文献处理、题目画像和对账等后台任务。

前端技术栈包括 React、TypeScript、Vite、React Router、TanStack Query、Zustand、Axios、Tailwind CSS 和 shadcn/ui 风格组件。其中 React 负责组件化 UI，TypeScript 提供静态类型约束，Vite 提供开发服务器和构建能力，React Router 负责路由，TanStack Query 负责服务端数据请求和缓存，Zustand 负责轻量状态管理，Axios 负责 HTTP 请求封装，Tailwind CSS 负责样式组织。

后端技术栈包括 Python、Flask、Flask-SQLAlchemy、Flask-Migrate、Flask-JWT-Extended、PyYAML、pypdf、jieba、redis、pytest、import-linter 和 openapi-spec-validator。Flask 提供 API 服务，SQLAlchemy 提供 ORM 映射，Alembic/Flask-Migrate 管理数据库迁移，JWT 承担认证机制，pypdf 用于 PDF 文本提取，jieba 用于中文关键词处理，redis 用于任务队列，pytest 用于测试，import-linter 用于架构约束检测，OpenAPI 契约用于接口规范校验。

系统的本地运行环境由 Docker Compose 组织，包括 web、worker、postgres 和 redis 四个核心服务。web 服务运行 Flask API，worker 服务循环消费队列任务，postgres 服务保存业务数据，redis 服务承担 broker。前端通过 Vite 开发服务器运行，并将 /api/v1 请求代理到后端默认端口。

3.3 后端分层设计

【图片占位：图 3-2 后端分层架构图。建议展示 API 层、Service 层、Use Cases 层、Task/Worker 层、Adapter 层、Model 层和 Common 基础层的依赖方向。】
图 3-2 后端分层架构图


后端按照职责拆分为 API、Service、Use Cases、Task/Worker、Adapter、Model 和 Common 等层。

API 层负责 HTTP 请求边界，包括参数校验、鉴权上下文、调用 Service、序列化响应和状态码映射。API 层不直接访问 Adapter、Use Cases、Task 或 ORM Model，以避免路由层承担过多业务职责。

Service 层是领域业务入口，负责事务处理、业务规则校验、Policy 检查、数据库读写和任务入队决策。例如 ChatService 负责创建会话和发送消息的受理流程，DocumentService 负责创建文档任务和入队 PDF 解析，TopicService 负责课题创建更新和题目画像任务触发，SelectionService 负责志愿决策与指导关系维护，RecommendService 负责只读推荐排序。

Use Cases 层是编排层，负责复杂业务流程的组织，尤其是需要调用 Adapter 的任务。例如聊天编排负责构建上下文消息并调用 LLM Adapter，文档流水线负责 PDF 文本处理和分块摘要，题目关键词与画像逻辑负责任务画像分析。将编排逻辑集中在 Use Cases 层，有助于避免 Service 层和 Worker 层重复维护提示词、分块策略和外部调用顺序。

Task/Worker 层负责异步任务。task.queue 提供入队门面，chat_jobs、pdf_parse_jobs、document_jobs、keyword_jobs 和 reconcile_jobs 等模块负责消费对应队列。Worker 模块本身只做 payload 校验、调用 Use Cases、状态回写和错误处理，不直接 import Adapter，保证外部调用路径受控。

Adapter 层负责隔离外部系统和第三方能力，包括 LLM、PDF、NLP 和 Storage 等。通过 Adapter 层封装，业务代码不直接绑定具体厂商 SDK 或 HTTP 接口，便于在开发、测试和演示环境中切换 mock 与真实服务。

Model 层负责数据库实体定义和序列化转换，Common 层提供错误封装、Policy、配置和基础设施能力。通过上述分层，系统能够在功能扩展时保持清晰的依赖方向。

3.4 前端总体设计

【图片占位：图 3-3 前端页面与模块结构图。建议展示 /login、/app/dashboard、/app/topics、/app/chat、/app/documents、/app/taskboard 与 features、components、lib 等目录之间的关系。】
图 3-3 前端页面与模块结构图


前端定位为围绕毕业设计选题双向选择展开的业务系统，而不是普通后台管理页面。系统通过受保护路由进入 /app 后，提供 Dashboard、Topics、Chat、Documents 和 Taskboard 等主要页面，其中 Topics 是选题互选主页面，Chat、Documents 和 Taskboard 是围绕选题结果继续开展毕业设计的辅助页面。

Dashboard 是系统首页，聚合当前用户的题目、指导关系、文档任务、聊天会话和里程碑状态，并展示从题目画像到学生推荐、志愿确认和过程跟踪的选题闭环。Topics 页面是系统选题双向选择功能核心，包含题目浏览、教师题目分析、学生画像推荐、志愿提交和教师处理志愿等能力。Chat 页面用于展示异步聊天任务和消息流，为学生在选题后开展论文与系统设计提供问答辅助。Documents 页面用于展示 PDF 文档任务的创建、状态轮询和结果预览，为学生理解选题相关文献提供支持。Taskboard 页面用于管理毕业设计里程碑，并支持教师按指导学生查看任务。

前端在数据模型上遵循“接口 DTO 使用 snake_case、页面模型使用 camelCase”的原则，通过 features 目录中的 api、queries、types 和 utils 文件组织各业务域。服务端数据请求由 TanStack Query 管理，认证态由 Zustand 和本地存储共同维护。页面组件尽量通过共享组件和工具函数复用状态标签、空状态、统计卡片和错误适配逻辑。

3.5 数据库总体设计

【图片占位：图 3-4 数据库 E-R 图。建议展示 users、terms、topics、applications、assignments、milestones、conversations、messages、chat_jobs、document_tasks 和 document_artifacts 等核心实体及其关联。】
图 3-4 数据库 E-R 图


系统数据库以用户、学期、课题、题目画像、学生画像、志愿、指导关系、聊天、文档任务和里程碑为核心实体。其中课题、画像、志愿和指导关系直接服务于“智能双向选择”主流程，聊天、文档任务和里程碑服务于选题后的辅助过程。

用户相关数据包括用户基础信息、角色、认证字段和学生画像。学期数据用于组织毕业设计批次，并绑定大模型配置。课题数据包括题目标题、简介、要求、容量、已选人数、教师、状态和学期。题目画像数据可以存储在课题相关 JSON 字段或独立画像结构中，保存关键词、难度、能力要求、适合学生类型、风险和摘要等内容。

志愿与指导关系数据用于支撑双向选择。Application 表记录学生对题目的志愿申请、优先级和状态；Assignment 表记录最终形成的学生、教师、课题和学期之间的指导关系。由于指导关系是后续任务看板和教师查看学生进度的依据，因此系统将其作为独立真源数据维护。

聊天相关数据包括 Conversation、Message 和 ChatJob。Conversation 记录会话元数据，Message 记录用户消息和 assistant 占位或回复，ChatJob 记录异步任务状态。文档相关数据包括 DocumentTask 和 DocumentArtifact，记录 PDF 文件、任务类型、状态、处理阶段、进度、结果和错误信息。里程碑数据记录学生毕业设计过程任务及其状态。

3.6 接口与任务契约设计

【图片占位：图 3-5 异步任务状态流转图。建议展示 pending、running、done、failed 四种状态，以及 chat_jobs、pdf_parse、document_jobs、keyword_jobs、reconcile_jobs 的任务流转关系。】
图 3-5 异步任务状态流转图


系统后端以 OpenAPI 契约作为接口真源。HTTP 基路径为 /api/v1，主要接口包括 /auth/login、/users/me、/terms、/topics、/recommendations/topics、/applications、/assignments、/milestones、/conversations 和 /document-tasks 等。

异步任务统一使用 pending、running、done、failed 四种状态。聊天发送消息和文档上传任务采用 HTTP 202 受理模式，返回 job 或 task 信息后由前端轮询状态。错误响应采用统一 ErrorEnvelope 结构，包含 error.code、error.message 和可选 details。队列契约声明包括 chat_jobs、pdf_parse、document_jobs、keyword_jobs 和 reconcile_jobs，分别对应聊天生成、PDF 解析、文档分析、题目画像和指导关系对账。

4 系统详细设计与实现

4.1 身份认证与学生画像模块设计与实现

【图片占位：图 4-1 用户登录与画像维护流程图。建议展示登录、令牌保存、获取 /users/me、更新学生画像和进入推荐页面的流程。】
图 4-1 用户登录与画像维护流程图


身份认证与学生画像模块为选题双向选择流程提供用户身份和匹配数据基础。用户通过登录接口提交用户名和密码，后端校验成功后返回访问令牌，并根据实现策略维护刷新令牌。前端在登录成功后保存认证态，并通过受保护路由控制未登录用户访问业务页面。

当前用户接口 /users/me 用于返回用户基本信息、角色信息和画像字段。学生画像是智能推荐模块的重要输入，包含兴趣、技能、关键词、目标和每周投入时间等字段。前端在 Topics 页面提供画像维护入口，学生保存画像后，推荐接口即可使用这些字段与题目画像进行匹配。通过将学生偏好和能力结构化，系统能够把“学生想做什么、能做什么、投入多少时间”转化为可计算的选题依据。

认证模块的设计重点是将身份上下文与业务角色分离。后端接口根据用户角色控制数据访问范围，例如学生只能维护自己的画像和志愿，教师只能处理与自己题目相关的申请，管理员能够维护学期和审核题目。前端则根据当前用户角色展示相应入口，但最终权限仍以后端校验为准。

4.2 课题管理与题目画像模块设计与实现

【图片占位：图 4-2 课题画像生成流程图。建议展示教师创建题目、TopicService 同步分词、keyword_jobs 入队、Worker 调用 Use Case、画像结果回写的流程。】
图 4-2 课题画像生成流程图


课题管理模块是智能双向选择系统的核心模块之一。教师可以创建题目，填写标题、简介、要求、容量和学期等信息。题目初始处于草稿或待审核状态，教师可提交审核，管理员可批准或驳回。题目发布后，学生可以在题目列表中浏览并提交志愿。与普通题目管理不同，本系统并不只保存题目文本，而是进一步分析题目内容，为推荐与互选提供结构化依据。

为了提升题目理解能力，系统在教师创建或更新题目后触发 keyword_jobs 队列任务。该任务的语义不只是简单关键词抽取，而是生成结构化题目画像。画像字段包括关键词、难度标签、难度原因、所需能力、适合学生类型、风险提示、摘要和提取时间。题目画像一方面帮助学生理解题目难度和要求，另一方面作为推荐模块的基础数据。

在实现上，TopicService 负责题目同步写入、业务状态校验和入队决策。题目保存后，系统提交事务并通过队列发送任务。Worker 消费 keyword_jobs 后调用题目画像相关编排逻辑，生成画像并写回数据库。当前实现支持基于文本信号的结构化分析，并预留通过 LLM Adapter 进行增强的扩展点。该方案使教师录题和画像生成解耦，避免题目保存接口被大模型调用耗时阻塞。

4.3 智能推荐模块设计与实现

【图片占位：图 4-3 智能推荐计算流程图。建议展示学生画像、题目画像、关键词归一化、Jaccard 打分、能力匹配、容量状态和解释结果生成过程。】
图 4-3 智能推荐计算流程图


智能推荐模块是连接“题目画像”和“学生画像”的核心模块，也是系统智能化选题能力的主要体现。推荐模块的目标是基于学生画像和题目画像输出可解释的课题推荐结果。与完全由大模型直接生成推荐不同，本系统采用“模型或分析逻辑负责题目画像，规则负责推荐排序”的设计。这样既能利用文本分析能力，又能保证推荐过程稳定、可解释、可测试。

学生画像包括 interests、skills、keywords、goal 和 weekly_hours 等字段。题目画像包括 keywords、required_capabilities、difficulty_label、risks 等字段。RecommendService 在接收到 /recommendations/topics 请求后，根据当前用户、学期和 Top-N 参数读取候选题目，并对学生画像与题目画像进行匹配计算。匹配维度包括技能命中、关键词命中、能力要求匹配、难度适配和容量状态等。

推荐结果不仅返回题目和分数，还返回 explain 字段。解释信息包括匹配技能、匹配关键词、匹配能力、难度适配、容量状态、风险提示和推荐理由。通过这些字段，学生能够理解系统为什么推荐某个题目，而不是只看到一个缺乏依据的排序列表。该设计紧贴“选题双向选择”标题要求：系统先帮助学生缩小题目范围，再由学生提交志愿、教师进行确认，最终仍保留师生双向选择的人工决策环节。

4.4 志愿填报、教师决策与指导关系模块设计与实现

【图片占位：图 4-4 志愿填报与教师决策流程图。建议展示学生提交志愿、教师接受或拒绝、生成 Assignment、更新 selected_count 和触发 reconcile_jobs 的流程。】
图 4-4 志愿填报与教师决策流程图


志愿填报、教师决策与指导关系模块共同构成“双向选择”的落地环节。学生可以在查看推荐解释和题目详情后，对感兴趣的题目提交志愿，并设置第一或第二志愿。系统记录 Application，包括学生、题目、学期、优先级和状态。学生在允许范围内可以撤销或修改志愿优先级。

教师在题目详情或教师分析页面查看学生申请，并结合题目要求、学生画像和志愿优先级对申请执行接受或拒绝操作。当教师接受某个申请时，系统需要保证多个数据的一致性：申请状态更新为 accepted，其他冲突申请需要按规则处理，Assignment 指导关系需要创建，题目的 selected_count 需要更新。上述操作应在同一事务中完成，避免出现申请已接受但指导关系未生成，或题目计数与实际指导关系不一致的情况。

在事务提交后，系统触发 reconcile_jobs 内部队列任务，用于对指导关系和题目已选人数等派生数据进行对账。该任务不暴露 REST 接口，只在内部消费。通过这种方式，系统能够在主流程保证事务一致性的同时，进一步提供后台校验和修复能力。

4.5 智能问答模块设计与实现

【图片占位：图 4-5 智能问答异步处理流程图。建议展示用户发送消息、创建 user 消息和 assistant 占位、生成 ChatJob、入队 chat_jobs、Worker 调用 LLM Adapter 并回写结果。】
图 4-5 智能问答异步处理流程图


智能问答模块是选题双向选择系统的辅助模块，用于在指导关系形成后为学生提供即时答疑支持。学生可以创建会话，围绕论文结构、技术实现、代码问题或文档理解进行提问。系统支持会话列表、会话详情、历史消息和发送用户消息。

由于大模型生成回复存在不确定耗时，系统采用异步受理设计。用户发送消息时，API 层调用 ChatService。ChatService 创建用户消息和 assistant 占位消息，生成 ChatJob，提交数据库事务后将任务入队到 chat_jobs。HTTP 接口立即返回 202，并携带 job_id、用户消息和 assistant 占位消息。前端展示占位消息并根据状态进行轮询。

Worker 消费 chat_jobs 后进入 Use Cases 编排层，构建系统提示、历史上下文和用户问题，并通过 LLM Adapter 调用外部模型或 mock provider。生成完成后，Worker 将 assistant 消息内容和任务状态回写为 done；如果发生错误，则将任务状态写为 failed 并记录错误信息。

这种设计使 API 进程不直接同步调用 LLM，保证了请求响应速度和系统稳定性。同时，Use Cases 层集中维护聊天编排逻辑，便于后续调整提示词、上下文裁剪策略和模型调用方式。

4.6 文献处理模块设计与实现

【图片占位：图 4-6 文献处理异步流程图。建议展示 PDF 上传、DocumentTask 创建、pdf_parse 解析、document_jobs 分析、DocumentArtifact 保存和任务状态回写。】
图 4-6 文献处理异步流程图


文献处理模块是围绕选题结果开展后续研究的辅助模块，用于帮助学生快速理解毕业设计相关资料。学生上传 PDF 文件时，DocumentService 负责校验文件和参数，保存文件或存储路径，创建 DocumentTask，并在事务提交后入队 pdf_parse。上传接口返回 202，前端展示任务状态。

Worker 首先消费 pdf_parse 队列，使用 PDF Adapter 提取文本，并将解析结果作为文档工件保存。随后系统根据文档任务类型触发 document_jobs，对文本进行分块摘要、结论提取或对比分析。对于较长文档，分块处理能够避免一次性提交过长上下文，提高处理稳定性。处理完成后，系统将摘要、要点、结果预览或错误信息写回 DocumentTask。

前端 Documents 页面展示文档任务列表、详情、状态和结果预览。任务处于 pending 或 running 时，前端按状态驱动进行轮询；任务进入 done 或 failed 后停止轮询。该设计与聊天模块的异步状态模型保持一致，降低了前端处理复杂度。

4.7 过程看板模块设计与实现

【图片占位：图 4-7 过程看板页面截图。建议放置 Taskboard 页面截图，体现里程碑任务、状态更新和教师按指导学生查看任务的界面。】
图 4-7 过程看板页面截图


过程看板模块用于将选题双向选择结果延伸到毕业设计执行阶段。学生可以创建里程碑任务，记录任务标题、计划时间、状态和说明，并在推进过程中更新任务状态。常见任务包括开题报告、需求分析、数据库设计、核心功能开发、系统测试、论文撰写和答辩准备等。

教师在接受学生志愿并形成指导关系后，可以通过 Taskboard 页面按学生查看里程碑任务。系统在查询里程碑时需要校验教师与学生之间的指导关系，防止教师访问无关学生任务。前端在存在指导关系时默认展示对应学生的任务上下文，并支持状态更新和删除操作。

过程看板模块的意义在于让“选题推荐”不只是一次性匹配，而是能够继续服务毕业设计全过程。通过任务状态，学生能够明确阶段目标，教师也可以更早发现进度滞后风险。

前端围绕登录页和工作台主布局组织。登录页负责认证入口，成功后进入受保护的 /app 路由。主布局包括左侧导航、顶部栏和内容区域，用户可以在 Dashboard、Topics、Chat、Documents 和 Taskboard 等页面之间切换。

5 系统测试

5.1 测试目标

系统测试的目标是验证功能正确性、接口契约一致性、异步任务可靠性、分层架构约束和前端页面行为。测试重点首先放在智能双向选择主流程上，包括题目创建、题目画像、学生画像、推荐解释、志愿提交、教师决策和指导关系生成；其次覆盖聊天、文档和任务看板等辅助模块。由于本系统既包含普通 CRUD 业务，也包含队列、Worker、文档处理和大模型适配等异步能力，因此测试不仅要覆盖接口返回结果，还要覆盖状态流转、任务入队、错误补偿和模块依赖边界。

6 总结与展望

6.1 工作总结

本文围绕“智能化毕业设计选题双向选择系统的设计与实现”开展研究和开发，针对传统毕业设计管理系统在题目理解不足、学生与题目匹配依据薄弱、师生互选过程缺少智能辅助等方面的不足，设计并实现了一个前后端分离的 Web 应用原型。

系统在业务上形成了较完整的智能双向选择闭环：教师发布题目后，系统生成题目画像；学生维护个人画像后，系统基于画像给出可解释推荐；学生结合推荐结果提交志愿后，教师进行接受或拒绝；接受后形成指导关系；后续通过任务看板跟踪毕业设计过程，并通过聊天和文档任务提供持续辅助。该闭环体现了系统“辅助师生完成高质量选题互选”而不仅是“记录流程状态”的核心定位。

系统在技术上采用 Flask、React、PostgreSQL、Redis 和 Docker Compose 等技术，按照 API、Service、Use Cases、Task/Worker、Adapter 和 Model 等层次进行设计。聊天、文档处理和题目画像等耗时任务通过队列和 Worker 异步执行，避免阻塞 API 请求。推荐模块采用题目画像和学生画像的规则匹配方式，保证结果可解释、可测试。系统还通过 OpenAPI 契约、自动化测试和架构约束脚本提升工程质量。

通过本课题的设计与实现，可以看出在毕业设计选题双向选择场景中引入 AI 能力具有现实价值，但 AI 更适合作为辅助分析和内容处理工具，而不是完全替代师生决策。将题目画像、学生画像、规则推荐、异步任务和可解释输出结合起来，是一种较适合本科毕业设计选题系统原型的实现路径。

6.2 不足之处

由于开发周期和实验条件有限，系统仍存在一些不足。

首先，题目画像当前已经具备结构化分析形态，但部分逻辑仍以规则和文本信号为主，尚未充分实现稳定的结构化 LLM 输出解析。如果要进一步提升智能化水平，需要增强提示词模板、JSON 输出校验、结果修复和人工确认机制。

其次，推荐算法仍属于轻量级规则匹配，没有引入更复杂的机器学习模型或历史选题效果反馈。当前方案适合小规模毕业设计场景和答辩演示，但在大规模真实使用中，还需要结合历年选题数据、学生成绩、项目经历和教师评价等信息进一步优化。

再次，系统的真实用户测试规模有限。虽然系统具备演示账号、运行脚本和自动化测试，但仍需要更多学生和教师参与试用，收集关于推荐准确性、题目画像可读性、页面易用性和任务看板实用性的反馈。

最后，系统在大模型服务接入方面仍需强化生产级能力，例如接口限流、成本控制、敏感信息保护、输出内容审核、失败重试策略和日志追踪等。

6.3 未来展望

后续工作可以从以下几个方向展开。

第一，增强题目画像与文档处理的 LLM 编排能力。可以将题目画像生成升级为严格的结构化输出流程，引入 JSON Schema 校验、失败重试、字段缺失补全和人工修订机制，使画像结果更加稳定可信。

第二，优化推荐算法。可以在现有规则匹配基础上，引入权重配置、历史反馈、协同过滤或语义向量匹配等方法，并允许教师和学生对推荐结果进行反馈，从而逐步形成更符合实际教学场景的推荐策略。

第三，完善双向选择后的过程质量监控。任务看板可以进一步扩展为进度预警、周报生成、教师反馈记录和材料提交提醒等功能，使系统在完成智能选题和指导关系确认后，继续覆盖毕业设计全过程。

第四，加强系统安全与部署能力。真实上线时需要完善权限审计、数据备份、HTTPS、日志脱敏、访问限流和容器化部署策略，并对大模型调用中的隐私数据进行更严格保护。

第五，扩大用户试用与评估。未来可以邀请更多学生和教师参与试用，从选题耗时、匹配满意度、文档阅读效率、任务完成率和系统易用性等指标评估系统效果，为后续改进提供数据支撑。

综上所述，本文设计并实现的智能化毕业设计选题双向选择系统，在传统毕业设计管理系统的基础上引入题目画像、学生画像、可解释推荐、志愿处理、指导关系确认、异步智能问答、文献处理和任务看板等能力，为毕业设计选题和后续过程推进提供了更具辅助性和智能化的支持。系统达到了预期设计目标，并为后续智慧教学管理系统的进一步研究和应用提供了可参考的工程实践。
