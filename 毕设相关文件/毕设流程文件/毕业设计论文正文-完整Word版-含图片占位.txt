摘要

毕业设计选题与师生双向选择是本科毕业设计过程的重要起点。针对传统毕业设计管理系统偏重流程记录、缺少题目要求分析、学生能力表达和推荐依据解释等问题，本文设计并实现了一套智能化毕业设计选题双向选择系统。系统面向学生、教师和管理员三类用户，围绕课题管理、题目画像、学生画像、智能推荐、志愿填报、教师决策和指导关系确认构建核心业务流程，并提供智能问答、文献处理和过程看板等选题后辅助功能。系统采用前后端分离架构，前端基于 React 和 TypeScript 构建单页应用，后端基于 Flask 提供 RESTful API，使用 PostgreSQL 保存业务数据，并通过 Redis 队列和 Worker 处理题目画像、文献解析和问答生成等异步任务。推荐模块将教师录入的题目文本转化为关键词、难度、能力要求和风险提示等题目画像，再结合学生兴趣、技能和投入时间生成规则化推荐结果及解释信息。测试与运行验证表明，系统能够支撑从教师录题、学生推荐、志愿提交、教师确认到指导关系形成及后续过程管理的主要业务闭环。该系统为高校毕业设计选题管理引入可解释智能辅助能力提供了一种可演示、可扩展的工程实现方案。

Design and Implementation of an Intelligent Two-way Selection System for Graduation Project Topics

Abstract

Graduation project topic selection and the two-way choice between students and supervisors are important starting points of undergraduate graduation projects. Existing graduation project management systems usually focus on process recording, such as topic application, volunteer submission, document submission and score management, but provide limited support for analyzing topic requirements, representing student abilities and explaining recommendation results. To address these problems, this thesis designs and implements an intelligent two-way selection system for graduation project topics. The system serves students, supervisors and administrators, and builds its main workflow around topic management, topic profiling, student profiling, intelligent recommendation, volunteer submission, supervisor decision-making and assignment confirmation. It also provides auxiliary functions such as intelligent question answering, literature processing and milestone tracking. The system adopts a front-end and back-end separated architecture. The front end is developed with React and TypeScript, the back end provides RESTful APIs with Flask, PostgreSQL stores business data, and Redis queues with worker processes handle asynchronous tasks. In the recommendation module, supervisor-entered topic descriptions are converted into topic profiles containing keywords, difficulty, required capabilities and risk hints. These profiles are matched with students' interests, skills and available time to generate rule-based recommendation results with explanations. Testing and operation verification show that the system can support the main business loop from topic publishing, recommendation and volunteer submission to supervisor confirmation, assignment formation and subsequent process management. The system provides a demonstrable and extensible engineering solution for introducing explainable intelligent assistance into graduation project topic management.

Keywords: graduation project, two-way selection, intelligent recommendation, topic profiling, asynchronous task

1 绪论

1.1 课题背景

毕业设计（论文）是本科教学体系中综合性较强的实践教学环节。对计算机类、软件工程类专业而言，毕业设计通常要求学生综合运用程序设计、数据库、网络通信、软件工程和系统测试等知识，围绕一个相对完整的问题完成需求分析、系统设计、编码实现、部署运行和论文表达。因此，毕业设计不仅检验学生的专业能力，也反映学校对实践教学过程的组织和管理水平。

在毕业设计全过程中，选题与师生双向选择处于起始位置。常见流程是教师发布题目、学院审核题目、学生浏览题目并填报志愿，教师再依据志愿和学生情况确认指导关系。该流程能够保留师生互选的基本形式，但在实际执行中容易出现信息不对称。学生面对多个题目时，通常只能根据题目名称、简短简介和个人直觉判断是否适合自己，难以准确把握题目所需技术基础、预期工作量、潜在风险以及与自身能力的匹配程度。教师筛选学生时，也往往缺少结构化的学生兴趣、已有技能和投入时间信息，只能依赖成绩、课堂印象或简单沟通进行判断。

随着高校信息化建设推进，许多毕业设计管理系统已经实现课题申报、志愿填报、过程材料提交和成绩评定等环节的线上化。已有研究中的毕业设计在线管理系统、B/S 管理系统和过程质量管理系统，通常能够降低纸质流转成本并提高管理效率[1-5]；本科毕业论文选题系统也开始关注导师选择、学生选题、题目审核、选题统计和在线沟通等功能[6-8]。但是，这类系统多侧重“流程是否完成”，对“题目需要什么能力”“学生适合哪些题目”“推荐依据是否可解释”“互选结果能否继续支撑后续过程管理”等问题支持不足。

近年来，大型语言模型和自然语言处理技术在文本理解、摘要生成、问答对话和关键词提取等任务中得到广泛应用[9-14]。这些技术为毕业设计选题场景提供了新的辅助方式：教师题目描述可以转化为较清晰的题目画像，学生兴趣和能力也可以通过结构化字段表达，再由系统生成可解释的选题推荐结果。基于此，本文围绕“智能化毕业设计选题双向选择系统的设计与实现”展开研究，重点探索如何在不替代师生判断的前提下，用结构化画像、规则推荐和异步智能辅助能力提升选题匹配与后续过程支撑效果。

本文研究范围限定在毕业设计选题及其后续辅助环节，不试图替代学校已有教务管理体系。系统以课题库和互选流程为主线，通过题目画像和学生画像提升匹配依据的清晰度，通过志愿填报和教师决策保留双向选择机制，通过指导关系确认把选题结果衔接到任务看板、文献处理和智能问答等过程支持功能中。

1.2 研究意义

本课题的研究意义主要体现在选题信息表达、智能辅助边界和工程实践三个方面。

首先，课题有助于提高毕业设计选题阶段的信息透明度。可解释推荐研究强调，推荐系统不应只给出排序结果，还应说明推荐依据，以提高透明度、可信度和用户满意度[15]。推荐系统相关研究也表明，推荐结果可以基于用户偏好、物品特征、历史交互、协同过滤、矩阵分解和神经协同过滤等方法生成[16-19]。在毕业设计场景中，题目和学生都具有较强的文本描述特征。将题目要求、能力基础、风险提示和学生兴趣、技能、投入时间等信息结构化，有助于降低学生盲目浏览和教师主观筛选带来的不确定性。

其次，课题有助于探索人工智能能力在教学管理场景中的适度应用。大型语言模型教育应用研究指出，LLM 可以用于摘要、反馈、写作辅助和学习支持，但也需要关注偏差、事实核验、误用和人工监督等问题[14]。人机 AI 交互研究同样强调系统应向用户呈现能力边界，并提供反馈和纠正机制[20]。因此，本文没有把推荐决策完全交给大模型，而是将大模型或自然语言处理能力主要用于题目理解、文献处理和智能问答等辅助环节，推荐排序则采用较容易解释和测试的规则方法。这样的设计更适合本科毕业设计系统的实现和答辩说明。

再次，课题能够体现现代 Web 工程方法在毕业设计管理系统中的综合应用。REST 架构强调客户端与服务端分离、无状态交互和统一接口等约束[21]。在此基础上，系统采用前后端分离、分层后端、接口契约、异步任务队列和自动化测试等工程方法，把选题业务、文档处理、智能问答和过程看板组织成可运行的应用原型。相比只完成页面展示或简单增删改查的系统，该课题更强调业务闭环、模块边界和可验证性。

最后，课题对高校毕业设计选题系统建设具有一定参考价值。本文并不追求覆盖教务管理的全部环节，而是围绕“教师录题、题目画像、学生画像、推荐解释、志愿提交、教师确认、指导关系形成”构建较完整的智能双向选择流程，并将选题结果延伸到后续任务管理和资料辅助中。该设计可以为传统毕业设计选题系统增加轻量化智能辅助能力提供实现样例。

1.3 国内外研究现状

围绕本课题，相关研究可以从毕业设计管理信息化、双向选择与推荐方法、自然语言处理与大模型教育应用三个方面进行梳理。

在毕业设计管理信息化方面，已有研究大多以提高教学管理效率为目标。早期毕业设计管理常依赖纸质材料和人工汇总，容易出现工作量大、状态追踪困难、材料归档不便等问题。针对这些问题，毕业设计在线管理系统、B/S 管理系统和过程质量管理系统通常围绕课题申报、题目审核、学生选题、文档提交、论文评阅、成绩管理和过程监控等功能展开[1-5]。这类研究说明，将毕业设计过程搬到线上能够降低纸质流转成本，提高教师、学生和管理人员之间的信息同步效率。

在本科论文选题与双向选择方面，已有研究进一步关注导师选择、在线选题、选题统计、学生文档上传和过程管理等功能[6-8]。这些系统能够支持学生填报志愿、教师确认学生、管理员统计选题结果等基本流程，也能够通过题目容量、志愿优先级和审核状态约束选题秩序。但是，从已有研究看，许多系统仍把题目看作普通文本或结构化表单，缺少对题目技术要求、难度、风险和适合学生类型的进一步分析；学生画像也往往只停留在基本身份信息或成绩信息层面，难以反映兴趣方向、技能基础和时间投入。也就是说，现有系统能够回答“流程是否完成”，但较难回答“为什么这个学生适合这个题目”。

在推荐方法方面，推荐系统研究为选题匹配提供了可借鉴的思路。传统推荐可以依据用户偏好、物品特征和历史交互进行建模，协同过滤、矩阵分解和神经协同过滤等方法已在多个推荐场景中得到应用[16-19]。可解释推荐研究则进一步强调推荐结果需要给出理由，使用户能够理解系统依据[15]。毕业设计选题场景与一般商品推荐不同：题目数量相对有限，历史交互数据不足，且教师和学生都需要保留最终判断权。因此，本文没有采用复杂黑箱模型，而是使用题目画像与学生画像之间的规则化匹配，优先保证结果可解释、可复核和可答辩。

在自然语言处理和大模型应用方面，Transformer、BERT 和检索增强生成等研究分别为注意力建模、预训练语言理解和知识密集型文本处理提供了重要基础[10-12]。高等教育和学术场景中的 LLM 研究表明，大模型可以用于内容生成、摘要、学习反馈、写作辅助和资料整理，但也存在事实准确性、偏差、误用和人工监督等风险[9,13-14]。人机 AI 交互准则也要求系统让用户了解能力边界，并支持反馈、纠正和控制[20]。这些研究说明，AI 能力适合作为毕业设计过程中的辅助工具，但不宜直接替代师生决策。

综上，已有研究在毕业设计流程信息化和在线选题方面已经形成较多实践，推荐系统和大模型研究也为智能辅助提供了方法基础。但在毕业设计选题这一具体场景中，仍存在三个不足：一是题目文本没有充分转化为可计算、可解释的题目画像；二是学生兴趣、技能和投入时间缺少结构化表达；三是选题结果与后续文献处理、智能问答和过程看板之间衔接不够紧密。本文的研究正是针对这些不足，设计一个围绕选题双向选择展开的智能辅助系统。

1.4 本文主要研究内容

本文围绕智能化毕业设计选题双向选择系统的设计与实现展开，主要研究内容如下。

第一，进行业务需求分析。本文围绕学生、教师和管理员三类角色，梳理课题发布、题目审核、题目画像、学生画像、智能推荐、志愿填报、教师决策和指导关系确认等核心需求，并分析智能问答、文献处理和过程看板等选题后辅助需求。在此基础上，进一步提出系统在可维护性、可测试性、可部署性和异步任务可靠性方面的非功能要求。

第二，完成系统架构与数据模型设计。系统采用前后端分离的 B/S 架构，后端按照 API、Service、Use Cases、Task/Worker、Adapter、Model 等层次组织，前端围绕 Dashboard、Topics、Chat、Documents 和 Taskboard 等页面构建业务入口。数据库围绕用户、学期、课题、志愿、指导关系、里程碑、会话、消息、聊天任务和文档任务等实体建模，支撑选题和选题后辅助功能。

第三，实现核心业务与智能辅助模块。系统实现登录认证、课题管理、题目画像生成、学生画像维护、推荐解释、志愿提交、教师处理志愿和指导关系生成等核心功能；同时实现智能问答、PDF 文献处理、异步 Worker 消费和过程看板等辅助模块，使系统能够从选题匹配延伸到毕业设计过程推进。

第四，开展系统测试与运行验证。本文通过后端 Pytest、架构约束测试、接口契约校验、前端构建检查和本地联调验证系统功能。测试重点覆盖题目画像、推荐解释、志愿处理、指导关系、异步任务状态流转和前端页面行为，以确认系统能够支撑毕业设计选题双向选择的主要业务闭环。

2 系统需求分析

2.1 可行性分析

从技术可行性看，本系统采用的 Flask、React、PostgreSQL、Redis、Docker Compose 等技术均为成熟开源技术，具有稳定的生态和丰富的工程实践。Flask 适合构建轻量级 RESTful API，React 和 TypeScript 适合实现复杂的前端交互，PostgreSQL 能够支撑关系型数据持久化，Redis 能够承担轻量级任务队列和状态缓存，Docker Compose 则便于在本地和演示环境中快速启动完整系统。REST 架构强调统一接口、无状态交互和客户端与服务端分离等思想，可作为系统 API 设计的理论依据[21]。系统所需的大模型能力通过 Adapter 层进行封装，既可对接真实 OpenAI-compatible HTTP 服务，也可在演示和测试环境中使用 mock provider，降低外部依赖对系统可运行性的影响。

从经济可行性看，系统主要依赖开源框架和本地容器化环境，不需要采购专用硬件。大模型接口采用可配置方式接入，在毕业设计原型阶段可以使用 mock 或低频调用方式完成验证，避免高额训练和推理成本。系统没有自行训练推荐模型，而是采用题目画像与学生画像的规则匹配策略，这种方案开发成本较低、实现周期可控，也更符合本科毕业设计对工程完整性和可解释性的要求。推荐系统和可解释推荐相关研究为后续算法扩展提供了协同过滤、特征匹配、矩阵分解和神经协同过滤等可参考方向[15-19]。

从操作可行性看，系统面向学生和教师的业务流程与实际毕业设计选题流程一致。学生登录后维护个人画像、浏览题目、查看推荐解释并提交志愿；教师发布题目、查看题目画像、处理学生志愿并形成指导关系；管理员维护学期和审核题目。在指导关系形成后，学生和教师再使用聊天、文档和任务看板等辅助功能推进毕业设计过程。系统页面围绕选题核心流程组织，学习成本较低，适合答辩演示和小规模试用。

2.2 角色分析

系统主要包括学生、教师和管理员三类用户。

学生是系统的主要使用者之一。学生登录后可以查看当前学期题目列表，维护个人画像，获取系统推荐的课题，查看推荐解释，提交第一或第二志愿，撤销或调整志愿。指导关系形成后，学生可以继续维护毕业设计里程碑、查看任务状态、上传文献处理任务，并使用智能问答功能辅助论文和系统开发。

教师主要负责题目发布和选题确认。教师可以创建和更新毕业设计题目，提交题目审核，查看题目画像结果，查看学生对题目的志愿申请，接受或拒绝申请。教师接受志愿后，系统生成指导关系，并可通过任务看板查看指导学生的毕业设计进度。

管理员主要负责学期、题目审核和系统基础配置。管理员可以维护学期信息、选题窗口和学期级大模型配置，也可以审核教师提交的题目，确保系统数据处于规范状态。

从任务书要求和系统标题出发，本系统功能分为两类：一类是围绕“智能化毕业设计选题双向选择”的核心功能，包括课题管理、题目画像、学生画像、智能推荐、志愿填报、教师决策和指导关系；另一类是围绕毕业设计选题结果落地的辅助功能，包括智能问答、文献处理和过程看板。论文后续设计与实现也以核心选题互选链路为主线展开。

2.3.1 身份认证与用户画像需求

系统应支持用户登录、令牌刷新、登出和当前用户信息查询。登录成功后，前端保存认证态，并在后续请求中携带访问令牌。系统应支持读取和更新当前用户信息，其中学生画像是推荐功能的重要输入。学生画像包括兴趣方向、技能、关键词、目标和每周投入时间等字段。通过结构化画像，系统能够更好地分析学生与题目的匹配关系。

2.3.2 学期与配置管理需求

毕业设计选题通常以学期或届次为单位组织。系统应支持学期列表、新建学期、学期详情、学期更新以及学期级 LLM 配置维护。学期信息用于约束题目、志愿、推荐、聊天和文档任务的业务范围，避免不同届次或不同批次的数据混用。

2.3.3 课题管理与题目画像需求

教师应能够创建、编辑、删除或撤回题目，并提交管理员审核。题目包括标题、简介、要求、容量、学期、教师等基本字段。题目创建或更新后，系统应触发题目画像生成流程，提取关键词、难度标签、难度原因、所需能力、适合学生类型、风险提示和总结说明等信息。题目画像应在题目详情和推荐接口中被使用，为学生理解题目和系统推荐提供依据。

2.3.4 智能推荐与可解释输出需求

系统应根据学生画像与题目画像生成 Top-N 推荐列表。推荐功能不直接调用大模型，而是基于已生成的题目画像和学生画像进行规则排序。推荐结果应包含分数和解释信息，例如匹配技能、匹配关键词、匹配能力、难度适配、容量状态、风险提示和推荐理由。可解释输出有助于学生理解推荐依据，也便于教师和答辩评审理解系统逻辑。

2.3.5 志愿填报与指导关系需求

学生应能够针对题目提交志愿，并设置第一或第二志愿。教师应能够查看某个题目的学生申请，并对申请进行接受或拒绝。教师接受申请后，系统应生成指导关系，并维护题目已选人数等派生数据。为保证数据一致性，志愿接受过程需要在事务中更新申请状态、指导关系和题目计数，并在事务提交后触发内部对账任务。

2.3.6 智能问答需求

系统应支持毕业设计场景下的智能问答。学生可以创建会话、发送消息、查看历史消息和异步任务状态。由于大模型生成可能耗时较长，系统不应在 HTTP 请求线程中同步等待完整回答，而应在接收用户消息后创建用户消息和 assistant 占位消息，写入 ChatJob 后入队，由 Worker 消费队列并回写 assistant 回复。

2.3.7 文献处理需求

学生在毕业设计过程中需要阅读大量论文、技术文档和外文资料。系统应支持上传 PDF 文献并创建文档处理任务，任务类型包括摘要、结论提取和对比分析等。上传请求返回任务受理结果，后台 Worker 负责 PDF 文本解析、分块处理、摘要生成和结果回写。前端通过轮询任务状态展示 pending、running、done 和 failed 等状态。

2.3.8 过程看板需求

系统应支持毕业设计里程碑管理。学生可以创建、更新和删除里程碑任务，记录任务标题、状态、时间范围等信息。教师在形成指导关系后，可以按学生查看其任务进度。过程看板有助于将选题结果延伸到毕业设计中后期的过程管理，避免系统只停留在选题阶段。

2.4 非功能需求分析

系统的非功能需求主要包括性能、可靠性、可维护性、安全性和可测试性。

在性能方面，聊天消息发送和文献上传等耗时任务应采用异步受理方式。API 层只负责校验、落库和入队，并在较短时间内返回 202 状态，避免因外部大模型接口耗时导致请求阻塞。推荐接口属于同步只读接口，应基于数据库中已有画像快速计算并返回结果。

在可靠性方面，系统应保证数据库写入与队列入队之间的一致性。对于需要异步处理的任务，应先提交数据库占位记录，再执行入队操作；若入队失败，应进行失败补偿，避免任务长期处于 pending 状态。Worker 处理任务时应能够记录 running、done、failed 等状态，并在异常情况下写入错误码和错误信息。

在可维护性方面，系统采用分层架构，API 层只处理 HTTP 边界，Service 层处理业务事务和入队决策，Use Cases 层负责 LLM 和文档任务编排，Task/Worker 层负责队列消费，Adapter 层隔离外部服务，Model 层负责数据持久化。通过 import-linter 和静态脚本约束模块依赖，避免路由层直接访问模型、任务或外部 Adapter。

在安全性方面，系统应对不同角色进行访问控制。学生、教师和管理员只能访问与其身份相符的数据和操作。接口错误应使用统一错误结构返回，不暴露敏感实现细节。Refresh Token 和访问令牌应有清晰的生命周期控制。

在可测试性方面，系统应提供后端单元测试、集成测试、契约测试、架构约束测试和前端组件测试。大模型接口应通过 Adapter 层和 mock provider 隔离，使测试环境不依赖真实外部服务。

3 系统总体设计

3.1 系统设计目标

本系统的设计目标是实现一个功能完整、结构清晰、可运行、可测试、可演示的智能化毕业设计选题双向选择系统原型。系统应满足以下目标：

第一，形成完整的选题双向选择业务闭环。系统需要覆盖教师题目发布、题目画像生成、学生画像维护、智能推荐、志愿提交、教师处理志愿和指导关系生成等环节，使选题流程不再只是题目列表浏览和人工确认，而是具备数据分析、匹配推荐和互选确认能力。

第二，体现选题场景下的智能化辅助能力。系统应将自然语言处理和大模型能力优先用于题目分析与画像生成，通过学生画像和题目画像完成可解释推荐；文档处理和问答辅助则服务于选题后的毕业设计开展，作为系统智能化能力的补充。

第三，保证工程结构可维护。系统应避免将所有逻辑堆叠在路由或页面组件中，而是通过后端分层和前端模块化实现职责拆分。核心异步任务应通过队列和 Worker 完成，保证 API 响应稳定。

第四，便于部署和演示。系统应支持 Docker Compose 一键启动后端依赖服务，并通过 Vite 启动前端开发环境。演示环境应包含学生、教师和管理员账号，能够按照答辩演示链路完成操作。

3.2 系统技术架构

【图片占位：图 3-1 系统总体架构图。建议展示浏览器前端、Vite 代理、Flask API、PostgreSQL、Redis、Worker、LLM Adapter、PDF Adapter、NLP Adapter 和 Storage Adapter 之间的关系。】
图 3-1 系统总体架构图


系统采用前后端分离的 B/S 架构。REST 架构思想强调统一接口、客户端与服务端分离和无状态交互，适合前后端分离系统的接口设计[21]。基于该思想，前端运行在浏览器中，通过 HTTP 调用后端 RESTful API；后端运行 Flask API 服务，负责身份认证、业务处理、数据持久化和任务入队；PostgreSQL 负责业务数据存储；Redis 负责队列 broker 和部分状态能力；Worker 进程消费 Redis 队列并执行聊天生成、文献处理、题目画像和对账等后台任务。后端模块则依据身份认证、业务处理、异步任务、外部适配和数据持久化等职责划分边界。

前端技术栈包括 React、TypeScript、Vite、React Router、TanStack Query、Zustand、Axios、Tailwind CSS 和 shadcn/ui 风格组件。其中 React 负责组件化 UI，TypeScript 提供静态类型约束，Vite 提供开发服务器和构建能力，React Router 负责路由，TanStack Query 负责服务端数据请求和缓存，Zustand 负责轻量状态管理，Axios 负责 HTTP 请求封装，Tailwind CSS 负责样式组织。

后端技术栈包括 Python、Flask、Flask-SQLAlchemy、Flask-Migrate、Flask-JWT-Extended、PyYAML、pypdf、jieba、redis、pytest、import-linter 和 openapi-spec-validator。Flask 提供 API 服务，SQLAlchemy 提供 ORM 映射，Alembic/Flask-Migrate 管理数据库迁移，JWT 承担认证机制，pypdf 用于 PDF 文本提取，jieba 用于中文关键词处理，redis 用于任务队列，pytest 用于测试，import-linter 用于架构约束检测，OpenAPI 契约用于接口规范校验。

系统的本地运行环境由 Docker Compose 组织，包括 web、worker、postgres 和 redis 四个核心服务。web 服务运行 Flask API，worker 服务循环消费队列任务，postgres 服务保存业务数据，redis 服务承担 broker。前端通过 Vite 开发服务器运行，并将 /api/v1 请求代理到后端默认端口。

3.3 后端分层设计

【图片占位：图 3-2 后端分层架构图。建议展示 API 层、Service 层、Use Cases 层、Task/Worker 层、Adapter 层、Model 层和 Common 基础层的依赖方向。】
图 3-2 后端分层架构图


后端按照职责拆分为 API、Service、Use Cases、Task/Worker、Adapter、Model 和 Common 等层。

API 层负责 HTTP 请求边界，包括参数校验、鉴权上下文、调用 Service、序列化响应和状态码映射。API 层不直接访问 Adapter、Use Cases、Task 或 ORM Model，以避免路由层承担过多业务职责。

Service 层是领域业务入口，负责事务处理、业务规则校验、Policy 检查、数据库读写和任务入队决策。例如 ChatService 负责创建会话和发送消息的受理流程，DocumentService 负责创建文档任务和入队 PDF 解析，TopicService 负责课题创建更新和题目画像任务触发，SelectionService 负责志愿决策与指导关系维护，RecommendService 负责只读推荐排序。

Use Cases 层是编排层，负责复杂业务流程的组织，尤其是需要调用 Adapter 的任务。例如聊天编排负责构建上下文消息并调用 LLM Adapter，文档流水线负责 PDF 文本处理和分块摘要，题目关键词与画像逻辑负责任务画像分析。将编排逻辑集中在 Use Cases 层，有助于避免 Service 层和 Worker 层重复维护提示词、分块策略和外部调用顺序。

Task/Worker 层负责异步任务。task.queue 提供入队门面，chat_jobs、pdf_parse_jobs、document_jobs、keyword_jobs 和 reconcile_jobs 等模块负责消费对应队列。Worker 模块本身只做 payload 校验、调用 Use Cases、状态回写和错误处理，不直接 import Adapter，保证外部调用路径受控。

Adapter 层负责隔离外部系统和第三方能力，包括 LLM、PDF、NLP 和 Storage 等。通过 Adapter 层封装，业务代码不直接绑定具体厂商 SDK 或 HTTP 接口，便于在开发、测试和演示环境中切换 mock 与真实服务。

Model 层负责数据库实体定义和序列化转换，Common 层提供错误封装、Policy、配置和基础设施能力。通过上述分层，系统能够在功能扩展时保持清晰的依赖方向。

3.4 前端总体设计

前端定位为围绕毕业设计选题双向选择展开的业务系统，而不是普通后台管理页面。系统通过受保护路由进入 /app 后，提供 Dashboard、Topics、Chat、Documents 和 Taskboard 等主要页面，其中 Topics 是选题互选主页面，Chat、Documents 和 Taskboard 是围绕选题结果继续开展毕业设计的辅助页面。

Dashboard 是系统首页，聚合当前用户的题目、指导关系、文档任务、聊天会话和里程碑状态，并展示从题目画像到学生推荐、志愿确认和过程跟踪的选题闭环。Topics 页面是系统选题双向选择功能核心，包含题目浏览、教师题目分析、学生画像推荐、志愿提交和教师处理志愿等能力。Chat 页面用于展示异步聊天任务和消息流，为学生在选题后开展论文与系统设计提供问答辅助。Documents 页面用于展示 PDF 文档任务的创建、状态轮询和结果预览，为学生理解选题相关文献提供支持。Taskboard 页面用于管理毕业设计里程碑，并支持教师按指导学生查看任务。

前端在数据模型上遵循“接口 DTO 使用 snake_case、页面模型使用 camelCase”的原则，通过 features 目录中的 api、queries、types 和 utils 文件组织各业务域。服务端数据请求由 TanStack Query 管理，认证态由 Zustand 和本地存储共同维护。页面组件尽量通过共享组件和工具函数复用状态标签、空状态、统计卡片和错误适配逻辑。

3.5 数据库总体设计

【图片占位：图 3-3 数据库 E-R 总览图。建议展示 users、terms、topics、applications、assignments、milestones、conversations、messages、chat_jobs、document_tasks 和 document_artifacts 等核心实体及其总体关联。】
图 3-3 数据库 E-R 总览图


系统数据库以用户、学期、课题、题目画像、学生画像、志愿、指导关系、聊天、文档任务和里程碑为核心实体。其中课题、画像、志愿和指导关系直接服务于“智能双向选择”主流程，聊天、文档任务和里程碑服务于选题后的辅助过程。数据库实体设计围绕关系模型、主外键约束和数据一致性原则展开。

用户相关数据包括用户基础信息、角色、认证字段和学生画像。学期数据用于组织毕业设计批次，并绑定大模型配置。课题数据包括题目标题、简介、要求、容量、已选人数、教师、状态和学期。题目画像数据可以存储在课题相关 JSON 字段或独立画像结构中，保存关键词、难度、能力要求、适合学生类型、风险和摘要等内容。

志愿与指导关系数据用于支撑双向选择。Application 表记录学生对题目的志愿申请、优先级和状态；Assignment 表记录最终形成的学生、教师、课题和学期之间的指导关系。由于指导关系是后续任务看板和教师查看学生进度的依据，因此系统将其作为独立真源数据维护。

聊天相关数据包括 Conversation、Message 和 ChatJob。Conversation 记录会话元数据，Message 记录用户消息和 assistant 占位或回复，ChatJob 记录异步任务状态。文档相关数据包括 DocumentTask 和 DocumentArtifact，记录 PDF 文件、任务类型、状态、处理阶段、进度、结果和错误信息。里程碑数据记录学生毕业设计过程任务及其状态。

3.6 接口与任务契约设计

【图片占位：图 3-4 异步任务状态流转图。建议展示 pending、running、done、failed 四种状态，以及 chat_jobs、pdf_parse、document_jobs、keyword_jobs、reconcile_jobs 的任务流转关系。】
图 3-4 异步任务状态流转图


系统后端以 OpenAPI 契约作为接口真源。HTTP 基路径为 /api/v1，主要接口包括 /auth/login、/users/me、/terms、/topics、/recommendations/topics、/applications、/assignments、/milestones、/conversations 和 /document-tasks 等。

异步任务统一使用 pending、running、done、failed 四种状态。聊天发送消息和文档上传任务采用 HTTP 202 受理模式，返回 job 或 task 信息后由前端轮询状态。错误响应采用统一 ErrorEnvelope 结构，包含 error.code、error.message 和可选 details。队列契约声明包括 chat_jobs、pdf_parse、document_jobs、keyword_jobs 和 reconcile_jobs，分别对应聊天生成、PDF 解析、文档分析、题目画像和指导关系对账。

4 系统详细设计与实现

4.1 身份认证与学生画像模块设计与实现

身份认证与学生画像模块为选题双向选择流程提供用户身份和匹配数据基础。用户通过登录接口提交用户名和密码，后端校验成功后返回访问令牌，并根据实现策略维护刷新令牌。前端在登录成功后保存认证态，并通过受保护路由控制未登录用户访问业务页面。

当前用户接口 /users/me 用于返回用户基本信息、角色信息和画像字段。学生画像是智能推荐模块的重要输入，包含兴趣、技能、关键词、目标和每周投入时间等字段。前端在 Topics 页面提供画像维护入口，学生保存画像后，推荐接口即可使用这些字段与题目画像进行匹配。通过将学生偏好和能力结构化，系统能够把“学生想做什么、能做什么、投入多少时间”转化为可计算的选题依据。

认证模块的设计重点是将身份上下文与业务角色分离。后端接口根据用户角色控制数据访问范围，例如学生只能维护自己的画像和志愿，教师只能处理与自己题目相关的申请，管理员能够维护学期和审核题目。前端则根据当前用户角色展示相应入口，但最终权限仍以后端校验为准。

4.2 课题管理与题目画像模块设计与实现

【图片占位：图 4-1 课题画像生成流程图。建议展示教师创建题目、TopicService 同步分词、keyword_jobs 入队、Worker 调用 Use Case、画像结果回写的流程。】
图 4-1 课题画像生成流程图


课题管理模块是智能双向选择系统的核心模块之一。教师可以创建题目，填写标题、简介、要求、容量和学期等信息。题目初始处于草稿或待审核状态，教师可提交审核，管理员可批准或驳回。题目发布后，学生可以在题目列表中浏览并提交志愿。与普通题目管理不同，本系统并不只保存题目文本，而是进一步分析题目内容，为推荐与互选提供结构化依据。

为了提升题目理解能力，系统在教师创建或更新题目后触发 keyword_jobs 队列任务。该任务的语义不只是简单关键词抽取，而是生成结构化题目画像。画像字段包括关键词、难度标签、难度原因、所需能力、适合学生类型、风险提示、摘要和提取时间。题目画像一方面帮助学生理解题目难度和要求，另一方面作为推荐模块的基础数据。

在实现上，TopicService 负责题目同步写入、业务状态校验和入队决策。题目保存后，系统提交事务并通过队列发送任务。Worker 消费 keyword_jobs 后调用题目画像相关编排逻辑，生成画像并写回数据库。当前实现支持基于文本信号的结构化分析，并预留通过 LLM Adapter 进行增强的扩展点。该方案使教师录题和画像生成解耦，避免题目保存接口被大模型调用耗时阻塞。

4.3 智能推荐模块设计与实现

【图片占位：图 4-2 智能推荐计算流程图。建议展示学生画像、题目画像、关键词归一化、Jaccard 打分、能力匹配、容量状态和解释结果生成过程。】
图 4-2 智能推荐计算流程图


智能推荐模块是连接“题目画像”和“学生画像”的核心模块，也是系统智能化选题能力的主要体现。推荐系统研究表明，推荐结果通常可以结合用户偏好、物品特征和历史交互生成[16-17]；可解释推荐研究进一步强调，推荐系统需要向用户说明推荐原因，以提升透明度和可信度[15]。与完全由大模型直接生成推荐不同，本系统采用“模型或分析逻辑负责题目画像，规则负责推荐排序”的设计。这样既能利用文本分析能力，又能保证推荐过程稳定、可解释、可测试。

学生画像包括 interests、skills、keywords、goal 和 weekly_hours 等字段。题目画像包括 keywords、required_capabilities、difficulty_label、risks 等字段。RecommendService 在接收到 /recommendations/topics 请求后，根据当前用户、学期和 Top-N 参数读取候选题目，并对学生画像与题目画像进行匹配计算。匹配维度包括技能命中、关键词命中、能力要求匹配、难度适配和容量状态等。上述匹配过程主要采用规则化特征匹配；其后续扩展可参考可解释推荐、推荐系统特征建模以及词向量语义相似度计算等研究[15-17,22]。

推荐结果不仅返回题目和分数，还返回 explain 字段。解释信息包括匹配技能、匹配关键词、匹配能力、难度适配、容量状态、风险提示和推荐理由。通过这些字段，学生能够理解系统为什么推荐某个题目，而不是只看到一个缺乏依据的排序列表。该设计紧贴“选题双向选择”标题要求：系统先帮助学生缩小题目范围，再由学生提交志愿、教师进行确认，最终仍保留师生双向选择的人工决策环节。

4.4 志愿填报、教师决策与指导关系模块设计与实现

【图片占位：图 4-3 志愿填报与教师决策流程图。建议展示学生提交志愿、教师接受或拒绝、生成 Assignment、更新 selected_count 和触发 reconcile_jobs 的流程。】
图 4-3 志愿填报与教师决策流程图


志愿填报、教师决策与指导关系模块共同构成“双向选择”的落地环节。学生可以在查看推荐解释和题目详情后，对感兴趣的题目提交志愿，并设置第一或第二志愿。系统记录 Application，包括学生、题目、学期、优先级和状态。学生在允许范围内可以撤销或修改志愿优先级。

教师在题目详情或教师分析页面查看学生申请，并结合题目要求、学生画像和志愿优先级对申请执行接受或拒绝操作。当教师接受某个申请时，系统需要保证多个数据的一致性：申请状态更新为 accepted，其他冲突申请需要按规则处理，Assignment 指导关系需要创建，题目的 selected_count 需要更新。上述操作应在同一事务中完成，避免出现申请已接受但指导关系未生成，或题目计数与实际指导关系不一致的情况。

在事务提交后，系统触发 reconcile_jobs 内部队列任务，用于对指导关系和题目已选人数等派生数据进行对账。该任务不暴露 REST 接口，只在内部消费。通过这种方式，系统能够在主流程保证事务一致性的同时，进一步提供后台校验和修复能力。

4.5 智能问答模块设计与实现

智能问答模块是选题双向选择系统的辅助模块，用于在指导关系形成后为学生提供即时答疑支持。学生可以创建会话，围绕论文结构、技术实现、代码问题或文档理解进行提问。系统支持会话列表、会话详情、历史消息和发送用户消息。

大型语言模型和预训练语言模型研究表明，相关模型可用于文本生成、问答、语言理解和教育辅助等任务[9-11,13-14]。由于大模型生成回复存在不确定耗时，系统采用异步受理设计。用户发送消息时，API 层调用 ChatService。ChatService 创建用户消息和 assistant 占位消息，生成 ChatJob，提交数据库事务后将任务入队到 chat_jobs。HTTP 接口立即返回 202，并携带 job_id、用户消息和 assistant 占位消息。前端展示占位消息并根据状态进行轮询。该设计将大模型能力限定在辅助问答场景中，并通过异步任务降低生成式模型耗时和不确定性对主业务流程的影响。

Worker 消费 chat_jobs 后进入 Use Cases 编排层，构建系统提示、历史上下文和用户问题，并通过 LLM Adapter 调用外部模型或 mock provider。生成完成后，Worker 将 assistant 消息内容和任务状态回写为 done；如果发生错误，则将任务状态写为 failed 并记录错误信息。

这种设计使 API 进程不直接同步调用 LLM，保证了请求响应速度和系统稳定性。同时，Use Cases 层集中维护聊天编排逻辑，便于后续调整提示词、上下文裁剪策略和模型调用方式。

4.6 文献处理模块设计与实现

【图片占位：图 4-4 文献处理异步流程图。建议展示 PDF 上传、DocumentTask 创建、pdf_parse 解析、document_jobs 分析、DocumentArtifact 保存和任务状态回写。】
图 4-4 文献处理异步流程图


文献处理模块是围绕选题结果开展后续研究的辅助模块，用于帮助学生快速理解毕业设计相关资料。预训练语言模型、检索增强生成和大型语言模型教育应用研究表明，相关技术可用于语言理解、知识密集型文本处理、摘要和提纲生成等任务[11-12,14]。基于这一思路，学生上传 PDF 文件时，DocumentService 负责校验文件和参数，保存文件或存储路径，创建 DocumentTask，并在事务提交后入队 pdf_parse。上传接口返回 202，前端展示任务状态。

Worker 首先消费 pdf_parse 队列，使用 PDF Adapter 提取文本，并将解析结果作为文档工件保存。随后系统根据文档任务类型触发 document_jobs，对文本进行分块摘要、结论提取或对比分析。对于较长文档，分块处理能够避免一次性提交过长上下文，提高处理稳定性。处理完成后，系统将摘要、要点、结果预览或错误信息写回 DocumentTask。

前端 Documents 页面展示文档任务列表、详情、状态和结果预览。任务处于 pending 或 running 时，前端按状态驱动进行轮询；任务进入 done 或 failed 后停止轮询。该设计与聊天模块的异步状态模型保持一致，降低了前端处理复杂度。

4.7 过程看板模块设计与实现

过程看板模块用于将选题双向选择结果延伸到毕业设计执行阶段。学生可以创建里程碑任务，记录任务标题、计划时间、状态和说明，并在推进过程中更新任务状态。常见任务包括开题报告、需求分析、数据库设计、核心功能开发、系统测试、论文撰写和答辩准备等。

教师在接受学生志愿并形成指导关系后，可以通过 Taskboard 页面按学生查看里程碑任务。系统在查询里程碑时需要校验教师与学生之间的指导关系，防止教师访问无关学生任务。前端在存在指导关系时默认展示对应学生的任务上下文，并支持状态更新和删除操作。

过程看板模块的意义在于让“选题推荐”不只是一次性匹配，而是能够继续服务毕业设计全过程。通过任务状态，学生能够明确阶段目标，教师也可以更早发现进度滞后风险。

6 总结

6.1 核心结论

本文围绕“智能化毕业设计选题双向选择系统的设计与实现”开展研究，针对传统毕业设计管理系统偏重流程记录、缺少题目理解和匹配解释的问题，设计并实现了一个面向学生、教师和管理员的 Web 应用原型。研究工作的总体结论是：在毕业设计选题场景中，智能化能力不宜直接替代师生判断，但可以通过题目画像、学生画像和可解释推荐降低信息不对称，并通过异步问答、文献处理和过程看板把选题结果继续延伸到毕业设计推进阶段。

6.2 主要成果与创新之处

本文的主要成果体现在三个方面。第一，围绕毕业设计选题双向选择构建了较完整的业务闭环。系统支持教师发布题目并生成题目画像，学生维护个人画像并查看推荐解释，学生提交志愿后由教师进行接受或拒绝，接受后形成指导关系，并进一步衔接任务看板、文献处理和智能问答等辅助功能。该流程使系统不只是记录选题状态，而是围绕“理解题目、匹配学生、解释推荐、确认关系、推进过程”形成连续支撑。第二，本文提出并实现了面向本科毕业设计场景的轻量级可解释推荐方案。系统没有将推荐决策完全交给大模型，而是将题目描述转化为关键词、难度、能力要求和风险提示等题目画像，再结合学生兴趣、技能和投入时间进行规则匹配，从而使推荐结果具有可解释、可测试和便于答辩说明的特点。第三，系统采用前后端分离、后端分层、接口契约、异步队列和自动化测试等工程方法，将聊天生成、文献解析和题目画像等耗时任务从 HTTP 请求线程中解耦，提高了系统结构的清晰度和可维护性。

本文工作的创新之处主要在于把“选题双向选择”这一具体教学管理场景与题目画像、学生画像、可解释推荐和异步智能辅助结合起来。相比普通题目列表和志愿表单，系统更强调推荐依据的表达和选题后过程的承接；相比完全依赖大模型生成结论的方案，系统保留教师和学生的最终决策权，把 AI 能力限定在分析、问答和文档辅助等环节。这种设计更符合本科毕业设计系统对可控性、可演示性和工程完整性的要求。

6.3 局限性

受开发周期、实验环境和数据规模限制，本文工作仍存在不足。题目画像生成虽然已经具备结构化形式，但部分分析仍依赖规则和文本信号，结构化大模型输出的稳定性、校验和人工修订机制还不充分。推荐算法仍属于轻量级规则匹配，没有引入历年选题数据、学生项目经历、教师评价和真实选题效果反馈。系统目前以原型验证和自动化测试为主，真实学生和教师参与试用的规模有限，对推荐准确性、页面易用性和过程看板实用性的评估还不够充分。此外，真实接入大模型服务时，还需要进一步完善限流、成本控制、隐私保护、内容审核、失败重试和日志追踪等生产级能力。

6.4 后续研究建议

后续研究可以从四个方向继续推进。第一，增强题目画像和文档处理的结构化生成能力，引入 JSON Schema 校验、失败重试、字段补全和人工确认机制，提高画像结果的稳定性。第二，在现有规则匹配基础上引入历史反馈、权重配置、语义向量匹配或协同过滤方法，使推荐策略更贴近真实教学场景。第三，扩大用户试用范围，从选题耗时、匹配满意度、推荐解释可理解性、文档阅读效率和任务完成率等指标评估系统效果。第四，加强系统安全和部署能力，完善权限审计、数据备份、日志脱敏、HTTPS、访问限流和大模型调用中的隐私保护。

总体而言，本文实现的系统为高校毕业设计选题管理引入可解释智能辅助能力提供了一种可运行、可扩展的工程方案，也为后续智慧教学管理系统的研究和应用提供了参考。
