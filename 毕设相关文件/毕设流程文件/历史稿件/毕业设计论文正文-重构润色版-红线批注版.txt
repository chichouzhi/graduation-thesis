1 绪论

1.1 课题背景

毕业设计（论文）是本科人才培养体系中综合性、实践性和评价性较强的重要教学环节。对于计算机类和软件工程类专业而言，毕业设计不仅要求学生综合运用程序设计、数据库、网络通信、软件工程、系统测试和项目部署等课程知识，还要求学生围绕真实或近真实问题完成需求分析、架构设计、编码实现、运行验证和论文表达。因此，毕业设计过程既是学生专业能力、工程素养和自主学习能力的集中体现，也是高校检验教学质量和实践教学组织能力的重要环节。

【修订建议 01｜用语精确性】“真实或近真实问题”略显口语化，建议改为“真实教学或工程场景中的问题”，语义更明确，也更符合工程类毕业设计论文表述习惯。

在毕业设计全过程中，选题是后续研究和开发工作的起点。选题质量直接影响学生后续任务的难度控制、技术路线选择、研究兴趣保持和最终成果质量。传统毕业设计选题流程通常包括教师申报题目、学院或管理员审核题目、学生浏览题目并填报志愿、教师根据学生志愿和个人判断确认指导关系等环节。该流程能够在形式上体现师生双向选择，但在实际执行中仍存在较为明显的信息不对称问题。学生面对大量题目时，往往只能依据题目名称、简短简介和个人直觉判断题目是否适合自身能力，难以准确把握题目所需技术基础、预期工作量、潜在风险和自身能力之间的匹配程度。教师筛选学生时，也常常缺少结构化的学生兴趣、技能储备和投入时间信息，只能依赖课程成绩、课堂印象或临时沟通进行判断，导致选题匹配效率和匹配质量受到限制。

【修订建议 02｜段落负载】本段信息量较大，包含选题重要性、传统流程和痛点分析三个层次。建议正式定稿时拆为两段：第一段说明选题的重要性和传统流程，第二段集中分析学生侧与教师侧的信息不对称问题。这样读者更容易抓住论文问题意识。

随着高校信息化建设不断推进，许多毕业设计管理系统已经实现课题申报、题目审核、志愿填报、过程材料提交、评阅和成绩管理等环节的线上化。已有毕业设计在线管理系统、B/S 管理系统和过程质量管理系统通常围绕出题、选题、文档提交、成绩评定和过程监控等功能展开，能够降低纸质流转成本并提高管理效率[1-5]。本科毕业论文选题系统进一步关注导师选择、学生选题、题目审核、选题统计和在线沟通等功能[6-8]。然而，从智能化选题辅助角度看，传统系统更多解决“流程能否在线完成”的问题，对于“题目需要什么能力”“学生适合哪些题目”“推荐依据是否可解释”“互选结果能否继续支撑过程管理”等问题支持不足。也就是说，现有系统在流程信息化方面已具备较成熟实践，但在选题匹配智能化、互选决策辅助化和选题后持续支撑方面仍存在进一步改进空间。

近年来，自然语言处理和大型语言模型技术快速发展，文本理解、摘要生成、关键词提取、问答对话和语义分析等能力不断增强。Transformer、BERT 和检索增强生成等研究分别为注意力建模、预训练语言理解和知识密集型文本处理提供了重要技术基础[12-14]。大型语言模型在教育场景中的应用研究也表明，其可用于内容生成、学习支持、摘要、提纲生成和个性化反馈等任务[20]。将上述能力适度引入毕业设计选题场景，有助于把教师输入的题目描述转化为题目画像，把学生输入的兴趣方向、技能基础和投入时间转化为学生画像，并在此基础上形成可解释的选题推荐结果，从而为学生选题和教师确认提供辅助依据。

基于上述背景，本文围绕“智能化毕业设计选题双向选择系统的设计与实现”开展研究，设计并实现一个前后端分离的 Web 应用原型。系统面向学生、教师和管理员三类角色，提供课题管理、题目画像、学生画像、智能推荐、志愿填报、教师决策、指导关系确认以及选题后的智能问答、文献处理和任务看板等功能。系统并不试图替代学校既有教务管理体系，而是聚焦毕业设计选题环节的智能化辅助，以“题目画像、学生画像、可解释推荐、志愿处理、指导关系形成”为主线，构建面向毕业设计选题双向选择的业务闭环。

1.2 研究意义

本课题具有较强的工程实践意义和应用探索价值。首先，本课题有助于提升毕业设计选题阶段的信息透明度。可解释推荐研究指出，推荐系统不应仅给出结果，还应说明推荐依据，以提高系统透明度、可信度和用户满意度[10]。推荐系统相关研究也表明，推荐结果可以基于用户偏好、物品特征、历史交互、协同过滤、矩阵分解和神经协同过滤等方法生成[11,17-19]。受此启发，本文设计的系统将教师录入的题目描述转化为结构化题目画像，包括关键词、难度标签、能力要求、适合学生类型和风险提示等信息；同时支持学生维护个人画像，包括兴趣方向、已有技能、关键词、目标和每周可投入时间等内容。在此基础上，系统通过规则化、可解释的推荐方式输出候选课题，使学生不再完全依赖主观浏览，也使教师能够更清晰地理解学生与题目的匹配依据。

其次，本课题探索了人工智能能力在毕业设计管理场景中的边界化应用。大型语言模型教育应用研究表明，LLM 在教育场景中具有内容生成、摘要、个性化反馈和学习支持等潜力，但也需要关注偏差、误用、事实核验和人工监督等问题[20]。人机 AI 交互研究也强调，系统应使用户理解智能能力边界，并提供反馈、纠正和控制机制[21]。基于上述原则，本文没有在推荐接口中直接调用大模型并由模型直接决定选题结果，而是将大模型能力主要用于题目画像分析、智能问答和文档辅助等环节；推荐结果则由可解释规则生成，以提高系统行为的可控性、可测试性和答辩可说明性。

【修订建议 03｜术语自然度】“边界化应用”不是常见学术搭配，建议改为“边界可控应用”或“有边界的辅助应用”。另外，“答辩可说明性”偏场景化，若想更正式，可改为“结果可解释性与工程可验证性”。

再次，本课题体现了现代 Web 工程方法在毕业设计系统中的综合应用。REST 架构强调客户端与服务端分离、无状态交互、统一接口和可扩展性等约束[15]。本文系统采用 Flask 后端、React 前端、PostgreSQL 数据库、Redis 队列、Docker Compose 部署和自动化测试等技术，并按照 API 层、Service 层、Use Cases 编排层、Task/Worker 层、Adapter 层和 Model 层进行组织。该架构能够降低模块耦合度，提高系统可维护性，并使聊天、文献处理和题目画像等耗时任务通过异步队列完成，避免阻塞 HTTP 请求。

最后，本课题对高校毕业设计选题系统建设具有一定参考意义。系统不是单纯的题目列表和志愿表单，而是围绕“教师录题、题目画像、学生画像、智能推荐、志愿提交、教师确认、指导关系形成”构建完整的智能双向选择流程；文档处理、智能问答和过程看板作为辅助模块，服务于选题结果落地后的毕业设计推进。该设计为传统毕业设计选题系统引入智能化辅助能力提供了一个轻量化、可演示、可扩展的工程样例。

1.3 国内外研究现状

毕业设计管理系统的相关研究主要集中在流程信息化、双向选择机制和智能辅助三个方向。

在流程信息化方面，较早的毕业设计管理主要依赖纸质材料和人工汇总，存在工作量大、状态追踪困难、材料归档不便等问题。已有毕业设计管理系统研究主要围绕课题申报、题目审核、学生选题、过程材料提交、论文评阅和成绩管理等功能展开，并指出相关系统能够提高教学管理效率[1-5]。本科毕业论文选题系统研究进一步关注导师选择、在线选题、选题统计、学生文档上传和过程管理等功能[6-8]。前后端分离架构能够增强系统交互体验和维护能力，使前端页面与后端业务服务通过 RESTful API 解耦开发，这与 REST 所强调的统一接口、客户端与服务端分离和无状态交互等思想一致[15]。

在双向选择机制方面，已有系统研究已经涉及题目审核、学生选题、导师选择、教师筛选学生、题目容量限制和选题过程管理等功能[1,6-8]。这些功能能够支撑线上互选流程，但匹配逻辑大多依赖结构化字段、志愿优先级、题目容量和人工判断。对于题目描述中隐含的技术要求、学生个人偏好与能力基础之间的语义关联，传统系统仍缺乏深入分析能力。因此，在选题双向选择场景中引入题目画像、学生画像和可解释推荐机制，具有进一步提升流程质量的现实需求。

在智能辅助方面，大型语言模型和自然语言处理技术为毕业设计支持系统提供了新的实现路径。Transformer、BERT 和检索增强生成研究分别说明了注意力机制、预训练语言表示和知识密集型文本处理的技术基础[12-14]。高等教育和学术场景中的 LLM 研究指出，大模型可以用于内容生成、个性化学习、摘要、写作辅助和学习支持，但也存在偏差、误用、事实核验、准确性和人工监督等问题[9,16,20]。人机 AI 交互准则也要求系统支持用户反馈、纠正和控制[21]。本文设计的系统正是在上述研究背景下，将 AI 能力作为辅助工具嵌入选题和过程支持环节，而不是让 AI 直接替代师生判断。

1.4 本文主要研究内容

本文围绕智能化毕业设计选题双向选择系统的设计与实现展开，主要研究内容包括以下四个方面。

第一，分析系统业务需求。本文围绕学生、教师和管理员等角色，重点梳理课题发布、题目画像、学生画像、智能推荐、志愿填报、教师决策和指导关系确认等选题双向选择需求，同时分析任务看板、智能问答和文献处理等选题后辅助需求，并从性能、可靠性、安全性、可维护性和可测试性等方面提出系统非功能需求。

第二，设计系统总体架构和数据模型。系统采用前后端分离的 B/S 架构，后端使用 Flask Application Factory 组织应用，并按照 API、Service、Use Cases、Task/Worker、Adapter、Model 等层次进行分层。前端使用 React、TypeScript、Vite、React Router、TanStack Query、Zustand、Axios 和 Tailwind CSS 构建单页应用。数据库采用 PostgreSQL，队列采用 Redis，部署采用 Docker Compose。数据模型围绕用户、学期、课题、志愿、指导关系、里程碑、会话、消息、聊天任务和文档任务等实体展开。

第三，实现核心业务模块。系统实现登录认证、当前用户信息维护、学期与配置管理、课题创建与审核、题目画像生成、学生画像维护、推荐结果解释、志愿提交与处理、指导关系生成等双向选择核心功能，并实现里程碑任务管理、聊天会话、文档任务和异步 Worker 消费等辅助功能，形成以选题互选为中心的毕业设计支持闭环。

第四，开展系统测试与验证。系统通过后端 Pytest、架构约束测试、契约校验、前端 Vitest、构建检查和本地 Docker Compose 联调，验证主要功能、接口契约、分层约束和异步处理流程的正确性。测试重点覆盖题目画像、推荐解释、志愿处理、指导关系、智能问答、文档处理和任务看板等关键功能。

2 系统需求分析

2.1 可行性分析

从技术可行性看，本系统采用的 Flask、React、PostgreSQL、Redis、Docker Compose 等技术均为成熟开源技术，具有稳定生态和丰富工程实践。Flask 适合构建轻量级 RESTful API，React 与 TypeScript 适合实现复杂前端交互，PostgreSQL 能够支撑关系型数据持久化，Redis 能够承担轻量级任务队列和状态缓存，Docker Compose 便于在本地和演示环境中快速启动完整系统。REST 架构强调统一接口、无状态交互和客户端与服务端分离等思想，可作为系统 API 设计的理论依据[15]。系统所需的大模型能力通过 Adapter 层进行封装，既可对接真实 OpenAI-compatible HTTP 服务，也可在演示和测试环境中使用 mock provider，从而降低外部依赖对系统可运行性的影响。

从经济可行性看，系统主要依赖开源框架和本地容器化环境，不需要采购专用硬件。大模型接口采用可配置方式接入，在毕业设计原型阶段可以通过 mock 或低频调用方式完成验证，避免高额训练和推理成本。系统没有自行训练推荐模型，而是采用题目画像与学生画像的规则匹配策略，该方案开发成本较低、实现周期可控，也更符合本科毕业设计对工程完整性和可解释性的要求。推荐系统和可解释推荐研究为后续算法扩展提供了协同过滤、特征匹配、矩阵分解和神经协同过滤等参考方向[10,11,17-19]。

从操作可行性看，系统面向学生和教师的业务流程与实际毕业设计选题流程基本一致。学生登录后维护个人画像、浏览题目、查看推荐解释并提交志愿；教师发布题目、查看题目画像、处理学生志愿并形成指导关系；管理员维护学期和审核题目。指导关系形成后，学生和教师可继续使用聊天、文档和任务看板等辅助功能推进毕业设计过程。系统页面围绕选题核心流程组织，学习成本较低，适合答辩演示和小规模试用。

从系统主题和毕业设计选题流程出发，本系统功能分为两类。一类是围绕“智能化毕业设计选题双向选择”的核心功能，包括课题管理、题目画像、学生画像、智能推荐、志愿填报、教师决策和指导关系。另一类是围绕选题结果落地的辅助功能，包括智能问答、文献处理和过程看板。论文后续设计与实现也以核心选题互选链路为主线展开。

2.3.1 身份认证与用户画像需求

系统应支持用户登录、令牌刷新、登出和当前用户信息查询。登录成功后，前端保存认证状态，并在后续请求中携带访问令牌。系统应支持读取和更新当前用户信息，其中学生画像是推荐功能的重要输入。学生画像包括兴趣方向、技能、关键词、目标和每周投入时间等字段。通过结构化画像，系统能够更好地分析学生与题目的匹配关系，并为推荐解释提供基础数据。

【修订建议 04｜需求表达边界】本节标题是“身份认证与用户画像需求”，但正文对教师、管理员画像或用户信息维护说明较少，容易让“用户画像”与“学生画像”混用。建议将标题改为“身份认证与学生画像需求”，或补充一句说明“本文所称画像主要指面向推荐功能的学生画像”。

2.3.2 学期与配置管理需求

毕业设计选题通常以学期或届次为单位组织。系统应支持学期列表、新建学期、学期详情、学期更新以及学期级 LLM 配置维护。学期信息用于约束题目、志愿、推荐、聊天和文档任务的业务范围，避免不同届次或不同批次的数据混用。学期级配置还可用于控制不同阶段的模型接入方式、选题窗口和演示环境参数。

2.3.3 课题管理与题目画像需求

教师应能够创建、编辑、删除或撤回题目，并提交管理员审核。题目包括标题、简介、要求、容量、学期和教师等基本字段。题目创建或更新后，系统应触发题目画像生成流程，提取关键词、难度标签、难度原因、所需能力、适合学生类型、风险提示和总结说明等信息。题目画像应在题目详情和推荐接口中被使用，为学生理解题目和系统推荐提供依据。

2.3.4 智能推荐与可解释输出需求

系统应根据学生画像与题目画像生成 Top-N 推荐列表。推荐功能不直接调用大模型，而是基于已生成的题目画像和学生画像进行规则排序。推荐结果应包含分数和解释信息，例如匹配技能、匹配关键词、匹配能力、难度适配、容量状态、风险提示和推荐理由。可解释输出有助于学生理解推荐依据，也便于教师和答辩评审理解系统逻辑。

2.3.5 志愿填报与指导关系需求

学生应能够针对题目提交志愿，并设置第一或第二志愿。教师应能够查看某个题目的学生申请，并对申请进行接受或拒绝。教师接受申请后，系统应生成指导关系，并维护题目已选人数等派生数据。为保证数据一致性，志愿接受过程需要在事务中更新申请状态、指导关系和题目计数，并在事务提交后触发内部对账任务。

2.3.6 智能问答需求

系统应支持毕业设计场景下的智能问答。学生可以创建会话、发送消息、查看历史消息和异步任务状态。由于大模型生成可能耗时较长，系统不应在 HTTP 请求线程中同步等待完整回答，而应在接收用户消息后创建用户消息和 assistant 占位消息，写入 ChatJob 后入队，由 Worker 消费队列并回写 assistant 回复。

2.3.7 文献处理需求

学生在毕业设计过程中需要阅读论文、技术文档和外文资料。系统应支持上传 PDF 文献并创建文档处理任务，任务类型包括摘要、结论提取和对比分析等。上传请求返回任务受理结果，后台 Worker 负责 PDF 文本解析、分块处理、摘要生成和结果回写。前端通过轮询任务状态展示 pending、running、done 和 failed 等状态。

2.3.8 过程看板需求

系统应支持毕业设计里程碑管理。学生可以创建、更新和删除里程碑任务，记录任务标题、状态、时间范围等信息。教师在形成指导关系后，可以按学生查看其任务进度。过程看板有助于将选题结果延伸到毕业设计中后期的过程管理，避免系统只停留在选题阶段。

2.4 非功能需求分析

系统的非功能需求主要包括性能、可靠性、可维护性、安全性和可测试性。

在性能方面，聊天消息发送、文献上传和题目画像生成等耗时任务应采用异步受理方式。API 层只负责校验、落库和入队，并在较短时间内返回结果，避免因外部大模型调用、PDF 解析或文本处理导致请求长时间阻塞。前端通过任务状态轮询展示处理进度，使用户能够理解系统当前状态。

在可靠性方面，系统应保证志愿处理、指导关系生成和题目计数更新的一致性。对于涉及多张表更新的核心操作，应使用事务机制；对于异步任务，应记录任务状态、错误信息和重试依据。当队列入队失败或外部服务异常时，系统应尽可能保留任务记录，并向前端返回明确状态，避免出现无反馈或状态不一致问题。

在可维护性方面，系统应采用清晰分层结构。API 层负责请求参数校验和响应转换，Service 层处理领域业务规则，Use Cases 层编排跨模块任务，Task/Worker 层处理异步消费，Adapter 层封装外部服务，Model 层负责数据持久化。通过分层约束，系统能够降低模块耦合，便于后续扩展推荐算法、替换模型服务或增加新的文档处理能力。

在安全性方面，系统应基于角色控制访问权限。学生只能维护自身画像、提交自身志愿和查看自身相关任务；教师只能处理自己题目的志愿申请，并查看已形成指导关系学生的任务进度；管理员负责学期、配置和审核管理。对于大模型和文档处理相关功能，应避免在日志中记录敏感信息，并在真实部署时进一步加强密钥管理、访问限流和内容审核。

在可测试性方面，系统应提供自动化测试覆盖核心功能、接口契约、异步任务和架构约束。推荐模块采用规则化实现，有利于构造稳定测试用例；Adapter 层支持 mock provider，有利于隔离外部 LLM 和 PDF 服务依赖；前后端通过 DTO 和契约校验降低接口不一致风险。

3 系统总体设计

3.1 系统设计目标

本系统的总体设计目标是构建一个围绕毕业设计选题双向选择的智能化辅助平台，使系统不仅能够记录选题流程状态，还能够为学生理解题目、教师理解学生和师生形成指导关系提供结构化支撑。

首先，系统应形成清晰的选题业务闭环。教师发布题目后，系统生成题目画像；学生维护个人画像后，系统根据学生画像和题目画像生成可解释推荐；学生结合推荐结果提交志愿；教师根据学生志愿和画像信息进行接受或拒绝；教师接受后系统生成指导关系，并将选题结果延伸到任务看板、智能问答和文档处理等后续辅助模块。

其次，系统应突出推荐结果的可解释性。毕业设计选题属于教学管理场景，推荐结果不能仅表现为一个分数，而应说明匹配依据。系统应展示关键词、技能、能力要求、难度适配和风险提示等解释信息，使学生能够理解为什么某个题目被推荐，也使教师能够判断推荐结果是否符合实际教学经验。

再次，系统应保证智能能力的边界可控。大模型能力主要用于题目画像、智能问答和文档辅助等环节，推荐排序不直接依赖模型生成结果，而是基于结构化画像进行规则计算。该设计既利用了自然语言处理能力，又避免让生成式模型直接决定选题结果，从而提高系统可测试性和可答辩性。

最后，系统应具备良好的工程可维护性。系统采用前后端分离、后端分层、异步任务队列和适配器封装等设计，使核心业务、外部模型调用和前端交互相互解耦，便于后续扩展和部署。

3.2 系统技术架构

【图片占位：图 3-1 系统总体架构图。建议展示浏览器前端、Vite 代理、Flask API、PostgreSQL、Redis、Worker、LLM Adapter、PDF Adapter、NLP Adapter 和 Storage Adapter 之间的关系。】
图 3-1 系统总体架构图

系统采用前后端分离的 B/S 架构。前端使用 React、TypeScript 和 Vite 构建单页应用，通过 React Router 组织路由，通过 TanStack Query 管理服务端状态和请求缓存，通过 Zustand 管理局部客户端状态，通过 Axios 统一封装 HTTP 请求。前端页面主要包括登录页、工作台、课题页、聊天页、文档页和过程看板页。

后端使用 Flask 构建 RESTful API，并通过 Application Factory 组织应用初始化。API 层对外提供身份认证、用户画像、学期、课题、推荐、志愿、指导关系、聊天、文档和里程碑等接口。数据库采用 PostgreSQL 存储用户、题目、志愿、指导关系、消息和任务等业务数据。Redis 用于实现轻量级任务队列，Worker 进程负责消费聊天、PDF 解析、文档处理、题目画像和内部对账等异步任务。

系统通过 Adapter 层封装外部依赖。LLM Adapter 用于对接 OpenAI-compatible HTTP 服务或 mock provider，PDF Adapter 用于解析上传文档，NLP Adapter 用于关键词处理和文本归一化，Storage Adapter 用于封装文件存储能力。通过适配器设计，系统能够在演示环境、测试环境和真实服务之间进行切换，降低外部服务变化对核心业务代码的影响。

部署方面，系统通过 Docker Compose 启动 PostgreSQL、Redis、Flask web 和 Worker 等服务，前端开发环境通过 Vite 代理将 /api/v1 请求转发至后端。该架构既适合本地开发和答辩演示，也为后续扩展到服务器部署提供基础。

3.3 后端分层设计

【图片占位：图 3-2 后端分层架构图。建议展示 API 层、Service 层、Use Cases 层、Task/Worker 层、Adapter 层、Model 层和 Common 基础层的依赖方向。】
图 3-2 后端分层架构图

后端采用分层设计，以降低模块耦合并明确职责边界。API 层负责接收 HTTP 请求、完成参数校验、调用业务服务并返回统一响应。该层不直接访问外部 LLM、PDF 解析器或底层队列细节，以避免接口层承担过多业务编排职责。

Service 层负责领域业务规则，是系统核心业务逻辑的主要承载位置。例如 TopicService 处理题目创建、更新、审核和画像任务触发；RecommendService 根据学生画像和题目画像计算推荐结果；SelectionService 处理志愿提交、教师决策、指导关系生成和题目计数维护；DocumentService 处理文档任务创建和入队补偿。Service 层既要保证业务规则完整，也要保持与具体外部模型服务解耦。

Use Cases 层用于编排跨模块或长流程任务。例如聊天任务需要读取会话上下文、构建提示词、调用 LLM Adapter 并回写消息；文档处理任务需要解析 PDF、切分文本、调用摘要能力并保存工件；题目画像任务需要结合题目描述、关键词处理和模型输出形成结构化画像。将这些流程放入 Use Cases 层，有利于避免 Service 层膨胀，也便于 Worker 复用。

Task/Worker 层负责从 Redis 队列中消费任务，并调用 Use Cases 层完成异步处理。Adapter 层负责封装 LLM、PDF、NLP 和存储等外部依赖。Model 层负责数据表映射和持久化。Common 基础层提供配置、错误处理、响应结构和工具函数等通用能力。系统还通过架构约束测试限制不合理依赖，例如 API 层不得直接 import Adapter，推荐域不得直接调用 LLM，从而保持架构边界稳定。

3.4 前端总体设计

【图片占位：图 3-3 前端页面与模块结构图。建议展示 /login、/app/dashboard、/app/topics、/app/chat、/app/documents、/app/taskboard 与 features、components、lib 等目录之间的关系。】
图 3-3 前端页面与模块结构图

前端以登录页和受保护的工作台布局为核心。用户访问系统后首先进入登录页，认证成功后进入 /app 路由。工作台布局包括左侧导航、顶部栏和内容区域，用户可以在 Dashboard、Topics、Chat、Documents 和 Taskboard 等页面之间切换。

Dashboard 页面用于聚合当前用户在系统中的关键状态，展示选题闭环进展、近期任务、异步任务状态和演示链路。Topics 页面是系统核心页面，承载题目浏览、教师录题、题目画像查看、学生画像维护、推荐解释、志愿提交和教师处理志愿等功能。Chat 页面用于智能问答，展示会话列表、消息流和任务状态。Documents 页面用于上传文档、查看文档处理任务和结果预览。Taskboard 页面用于维护毕业设计里程碑，并支持教师按指导关系查看学生进度。

前端数据请求由 TanStack Query 管理，能够统一处理请求缓存、加载状态、错误状态和轮询逻辑。Axios 封装统一请求实例，在请求中附带访问令牌并处理认证错误。状态映射工具函数用于把后端 pending、running、done 和 failed 等状态转换为前端展示语义。通过上述设计，前端页面能够围绕业务流程展开，同时保持接口调用和状态处理的统一性。

3.6 接口与任务契约设计

【图片占位：图 3-5 异步任务状态流转图。建议展示 pending、running、done、failed 四种状态，以及 chat_jobs、pdf_parse、document_jobs、keyword_jobs、reconcile_jobs 的任务流转关系。】
图 3-5 异步任务状态流转图

系统接口遵循 RESTful 风格，按资源和业务场景组织。身份认证接口提供登录、刷新令牌、登出和当前用户查询。用户接口支持学生画像读取和更新。学期接口提供学期列表、详情和配置维护。课题接口提供题目创建、更新、审核、详情和列表查询。推荐接口根据当前学生画像生成推荐结果。志愿接口支持学生提交志愿和教师处理申请。指导关系接口用于查询已形成的师生指导关系。聊天、文档和任务看板接口分别支撑选题后的智能问答、文献处理和进度管理。

异步任务契约采用统一状态模型，主要包括 pending、running、done 和 failed。pending 表示任务已创建但尚未执行；running 表示 Worker 正在处理；done 表示任务完成并已写回结果；failed 表示任务执行失败并记录错误信息。聊天任务、PDF 解析任务、文档分析任务、题目画像任务和对账任务均遵循该状态模型。统一任务契约有助于前端复用状态展示和轮询逻辑，也有助于后端统一处理错误和任务补偿。

4 系统详细设计与实现

4.1 身份认证与学生画像模块设计与实现

【图片占位：图 4-1 用户登录与画像维护流程图。建议展示登录、令牌保存、获取 /users/me、更新学生画像和进入推荐页面的流程。】
图 4-1 用户登录与画像维护流程图

身份认证模块是系统权限控制和业务访问的基础。用户通过登录接口提交账号和密码，后端校验通过后返回访问令牌和刷新令牌。前端保存认证状态，并在后续请求中携带访问令牌。用户进入工作台后，前端调用当前用户接口获取用户角色、基本信息和画像数据，并据此控制页面入口和操作权限。

学生画像是智能推荐的重要输入。系统允许学生维护兴趣方向、已有技能、关键词、目标和每周可投入时间等信息。画像字段采用结构化方式保存，以便推荐模块进行关键词匹配、技能匹配和难度适配判断。与仅依赖自由文本描述相比，结构化画像更有利于系统形成稳定、可测试的推荐逻辑，也便于学生在选题前主动补充自身能力信息。

在权限控制方面，学生只能维护自身画像，教师和管理员不能随意修改学生画像。前端在不同角色下展示不同功能入口，后端仍以角色校验作为最终权限边界。该设计避免仅依赖前端控制造成越权风险。

4.2 课题管理与题目画像模块设计与实现

【图片占位：图 4-2 课题画像生成流程图。建议展示教师创建题目、TopicService 同步分词、keyword_jobs 入队、Worker 调用 Use Case、画像结果回写的流程。】
图 4-2 课题画像生成流程图

课题管理模块承载教师发布题目和管理员审核题目的核心流程。教师创建题目时，需要填写标题、简介、要求、容量和所属学期等信息。题目创建后处于待审核或草稿状态，管理员审核通过后方可面向学生展示。教师也可以在审核前更新或撤回题目。通过审核状态控制，系统能够保证学生看到的题目具有基本规范性。

题目画像模块用于提升题目信息表达的结构化程度。传统题目描述往往以自然语言段落呈现，学生需要自行判断题目难度和能力要求。系统在题目创建或更新后触发画像生成流程，对题目标题、简介和要求进行分析，生成关键词、难度标签、难度原因、所需能力、适合学生类型、风险提示和总结说明等字段。题目画像既用于题目详情展示，也作为推荐模块的输入。

在实现上，TopicService 在题目创建或更新后完成基础保存，并触发 keyword_jobs 任务。Worker 消费任务后进入 Use Cases 层，调用 NLP Adapter 或 LLM Adapter 生成画像结果，并将结构化字段回写至 topics 表。对于演示和测试环境，系统可以使用 mock provider 生成稳定结果；对于真实部署环境，系统可以接入外部大模型服务。通过异步任务方式生成画像，系统避免在题目保存接口中同步等待模型返回，从而提高接口响应速度。

4.3 智能推荐模块设计与实现

【图片占位：图 4-3 智能推荐计算流程图。建议展示学生画像、题目画像、关键词归一化、Jaccard 打分、能力匹配、容量状态和解释结果生成过程。】
图 4-3 智能推荐计算流程图

智能推荐模块是系统体现“智能化选题辅助”的关键模块。推荐模块的输入包括学生画像、当前学期已发布题目和题目画像。系统首先对学生兴趣、技能和关键词进行归一化处理，再读取题目画像中的关键词、能力要求、难度标签和风险提示等字段，随后依据关键词重合度、技能匹配度、能力要求适配度、题目容量状态和难度适配情况计算推荐分数。

推荐结果采用 Top-N 形式返回。每个推荐项不仅包含题目基本信息和分数，还包含推荐解释。解释内容包括匹配关键词、匹配技能、匹配能力、难度适配说明、容量状态、风险提示和综合推荐理由。该设计使推荐结果从“黑箱分数”转变为“可理解的辅助建议”，有助于学生判断题目是否符合自身兴趣和能力，也有助于教师理解系统推荐依据。

推荐模块没有直接调用 LLM。其原因在于毕业设计选题具有较强的教学管理属性，推荐结果需要稳定、可复现和可解释。若由大模型直接生成推荐排序，系统行为可能受到模型输出随机性、提示词变化和外部服务状态影响。本文采用“模型辅助画像、规则生成推荐”的方式，将生成式能力限定在结构化分析环节，将推荐排序控制在可测试的规则逻辑中，从而兼顾智能化和可控性。

4.4 志愿填报、教师决策与指导关系模块设计与实现

【图片占位：图 4-4 志愿填报与教师决策流程图。建议展示学生提交志愿、教师接受或拒绝、生成 Assignment、更新 selected_count 和触发 reconcile_jobs 的流程。】
图 4-4 志愿填报与教师决策流程图

志愿填报与教师决策模块用于完成师生双向选择的正式确认。学生在浏览题目和查看推荐解释后，可以针对题目提交第一志愿或第二志愿。系统需要校验题目是否处于可选状态、是否属于当前学期、学生是否已经存在冲突申请以及志愿级别是否符合规则。提交成功后，教师可以在题目申请列表中查看学生申请信息，并根据题目要求、学生画像和沟通情况选择接受或拒绝。

教师接受学生志愿后，系统生成 assignment 记录，表示师生指导关系正式形成。与此同时，系统需要更新 application 状态和 topic 的已选人数。由于该过程涉及多张表更新，系统将接受操作放在事务中执行，确保申请状态、指导关系和题目计数保持一致。事务提交后，系统触发 reconcile_jobs 对账任务，用于检查题目已选人数等派生数据是否与实际指导关系一致。

该模块体现了系统对“双向选择”的业务理解。学生不是被动分配题目，而是在题目画像和推荐解释基础上主动提交志愿；教师也不是简单按照提交顺序确认，而是结合题目要求和学生情况作出决策。系统通过事务和对账机制保障流程结果可靠，通过指导关系记录把选题结果延伸到后续任务看板和过程管理。

4.5 智能问答模块设计与实现

【图片占位：图 4-5 智能问答异步处理流程图。建议展示用户发送消息、创建 user 消息和 assistant 占位、生成 ChatJob、入队 chat_jobs、Worker 调用 LLM Adapter 并回写结果。】
图 4-5 智能问答异步处理流程图

智能问答模块用于为学生在毕业设计过程中提供辅助咨询。学生可以围绕题目理解、技术方案、论文结构、文献阅读和开发问题创建会话并发送消息。考虑到大模型生成回复可能耗时较长，系统采用异步处理方式。用户发送消息后，API 层完成权限校验并创建用户消息，同时创建 assistant 占位消息和 ChatJob 任务。接口立即返回 202 状态，并携带 job_id、用户消息和 assistant 占位消息。前端展示占位消息，并根据任务状态进行轮询。

Worker 消费 chat_jobs 后进入 Use Cases 编排层，读取会话历史、构建系统提示和用户问题，并通过 LLM Adapter 调用外部模型或 mock provider。生成完成后，Worker 将 assistant 消息内容和任务状态回写为 done；如果发生错误，则将任务状态写为 failed 并记录错误信息。前端根据状态更新消息展示，使用户能够感知回复生成进度。

这种设计使 API 进程不直接同步调用 LLM，保证了请求响应速度和系统稳定性。同时，Use Cases 层集中维护聊天编排逻辑，便于后续调整提示词、上下文裁剪策略和模型调用方式。智能问答模块作为选题后辅助能力存在，不参与选题推荐的最终决策，从而保持系统核心互选流程的可控性。

4.6 文献处理模块设计与实现

【图片占位：图 4-6 文献处理异步流程图。建议展示 PDF 上传、DocumentTask 创建、pdf_parse 解析、document_jobs 分析、DocumentArtifact 保存和任务状态回写。】
图 4-6 文献处理异步流程图

文献处理模块用于帮助学生在选题后快速理解毕业设计相关资料。预训练语言模型、检索增强生成和大型语言模型教育应用研究表明，相关技术可用于语言理解、知识密集型文本处理、摘要和提纲生成等任务[13,14,20]。基于这一思路，系统支持学生上传 PDF 文献并创建文档处理任务，任务类型包括摘要、结论提取和对比分析等。

学生上传文件时，DocumentService 负责校验文件和参数，保存文件或存储路径，创建 DocumentTask，并在事务提交后入队 pdf_parse。上传接口返回 202 状态，前端展示任务已受理。Worker 首先消费 pdf_parse 队列，使用 PDF Adapter 提取文本，并将解析结果作为文档工件保存。随后系统根据文档任务类型触发 document_jobs，对文本进行分块摘要、结论提取或对比分析。对于较长文档，分块处理能够避免一次性提交过长上下文，提高处理稳定性。

处理完成后，系统将摘要、要点、结果预览或错误信息写回 DocumentTask。前端 Documents 页面展示文档任务列表、详情、状态和结果预览。任务处于 pending 或 running 时，前端按状态驱动进行轮询；任务进入 done 或 failed 后停止轮询。该设计与聊天模块的异步状态模型保持一致，降低了前端处理复杂度。

4.7 过程看板模块设计与实现

【图片占位：图 4-7 过程看板页面截图。建议放置 Taskboard 页面截图，体现里程碑任务、状态更新和教师按指导学生查看任务的界面。】
图 4-7 过程看板页面截图

过程看板模块用于将选题双向选择结果延伸到毕业设计执行阶段。学生可以创建里程碑任务，记录任务标题、计划时间、状态和说明，并在推进过程中更新任务状态。常见任务包括开题报告、需求分析、数据库设计、核心功能开发、系统测试、论文撰写和答辩准备等。通过里程碑任务，学生能够将毕业设计工作拆解为可跟踪的阶段目标。

教师在接受学生志愿并形成指导关系后，可以通过 Taskboard 页面按学生查看里程碑任务。系统在查询里程碑时校验教师与学生之间的指导关系，防止教师访问无关学生任务。前端在存在指导关系时默认展示对应学生的任务上下文，并支持状态更新和删除操作。

过程看板模块的意义在于让“选题推荐”不只是一次性匹配，而是能够继续服务毕业设计全过程。通过任务状态，学生能够明确阶段目标，教师也可以更早发现进度滞后风险，从而提高毕业设计过程管理的及时性。

4.8 前端页面实现

【图片占位：图 4-8 前端核心页面截图。建议放置 Dashboard、Topics、Chat、Documents 和 Taskboard 中最能体现系统闭环的页面截图，可组合为一张界面展示图。】
图 4-8 前端核心页面截图

前端围绕登录页和工作台主布局组织。登录页负责认证入口，成功后进入受保护的 /app 路由。主布局包括左侧导航、顶部栏和内容区域，用户可以在 Dashboard、Topics、Chat、Documents 和 Taskboard 等页面之间切换。

Dashboard 页面聚合系统关键数据，展示当前重点、统计卡片、近期工作、异步状态总览和答辩演示链路。该页面强调系统不是通用后台，而是围绕毕业设计选题双向选择形成的业务闭环，即教师题目画像、学生画像推荐、志愿提交确认和指导关系后的过程跟踪。

Topics 页面实现题目浏览、教师题目分析、学生推荐、志愿提交和教师处理志愿等功能，是系统业务闭环最集中的页面。学生可以维护画像并请求推荐结果，系统展示可解释推荐；教师可以创建题目、查看画像、查看学生志愿并进行决策。Chat 页面实现会话列表、消息流和 job 状态展示。Documents 页面实现文档任务列表、状态展示和结果预览。Taskboard 页面实现里程碑任务的创建、更新、删除和按指导关系查看。

前端通过 TanStack Query 管理数据请求和缓存，通过工具函数统一处理状态映射和错误提示。对于聊天和文档等异步任务，前端根据任务状态决定是否继续轮询。对于志愿处理和题目推荐等核心操作，前端在操作完成后刷新相关查询，使页面状态与后端数据保持一致。

5 系统测试

5.1 测试目标

系统测试的目标是验证功能正确性、接口契约一致性、异步任务可靠性、分层架构约束和前端页面行为。测试重点首先放在智能双向选择主流程上，包括题目创建、题目画像、学生画像、推荐解释、志愿提交、教师决策和指导关系生成；其次覆盖聊天、文档和任务看板等辅助模块。由于本系统既包含普通 CRUD 业务，也包含队列、Worker、文档处理和大模型适配等异步能力，因此测试不仅要覆盖接口返回结果，还要覆盖状态流转、任务入队、错误补偿和模块依赖边界。

5.2 后端测试

【图片占位：图 5-1 后端测试运行结果截图。建议放置 pytest、架构约束测试或 CI 测试结果截图。】

在架构测试方面，系统使用 import-linter 和静态检查脚本约束模块依赖。例如 API 层不得 import Adapter、Use Cases 或 Task；Task 层不得直接 import Adapter；推荐域不得调用 LLM；Service 层生产默认不得直连 LLM。通过这些测试，系统能够防止后续开发中出现破坏分层的隐性回归。

【修订建议 06｜数据精确性】“数百项”略显笼统。若可以从测试截图或命令输出获得准确数字，建议改为“共通过 X 项测试”；若无法确认准确数量，建议改为“完成了覆盖主要业务模块的 Pytest 验证”，避免量化表述缺乏证据。

综合测试结果表明，系统核心选题互选功能能够按预期运行，前后端接口契约基本一致，题目画像与推荐解释能够支撑学生选题决策，志愿处理与指导关系能够支撑教师确认流程；异步任务设计能够支撑聊天、文档和题目画像等耗时流程，分层约束能够有效限制不合理依赖。后续若接入真实大模型服务，还需要进一步补充真实接口调用的超时、限流、失败重试和内容质量评估测试。

6 总结与展望

6.1 工作总结

本文围绕“智能化毕业设计选题双向选择系统的设计与实现”开展研究和开发，针对传统毕业设计管理系统在题目理解不足、学生与题目匹配依据薄弱、师生互选过程缺少智能辅助等方面的不足，设计并实现了一个前后端分离的 Web 应用原型。

系统在业务上形成了较完整的智能双向选择闭环：教师发布题目后，系统生成题目画像；学生维护个人画像后，系统基于画像给出可解释推荐；学生结合推荐结果提交志愿后，教师进行接受或拒绝；接受后形成指导关系；后续通过任务看板跟踪毕业设计过程，并通过聊天和文档任务提供持续辅助。该闭环体现了系统“辅助师生完成高质量选题互选”而不仅是“记录流程状态”的核心定位。

系统在技术上采用 Flask、React、PostgreSQL、Redis 和 Docker Compose 等技术，按照 API、Service、Use Cases、Task/Worker、Adapter 和 Model 等层次进行设计。REST 架构思想为系统接口组织提供了客户端与服务端分离、无状态交互和统一接口等参考[15]。聊天、文档处理和题目画像等耗时任务通过队列和 Worker 异步执行，避免阻塞 API 请求。推荐模块采用题目画像和学生画像的规则匹配方式，保证结果可解释、可测试。系统还通过 OpenAPI 契约、自动化测试和架构约束脚本提升工程质量。

通过本课题的设计与实现可以看出，在毕业设计选题双向选择场景中引入 AI 能力具有现实价值，但 AI 更适合作为辅助分析和内容处理工具，而不是完全替代师生决策。高等教育和学术场景中的 LLM 研究已经指出，大模型具有教学辅助、写作辅助和研究辅助潜力，但同时存在准确性、偏差、伦理和人工监督等问题[9,16,20]；可解释推荐研究也强调推荐结果需要提供解释以提升透明度和可信度[10]。因此，将题目画像、学生画像、规则推荐、异步任务和可解释输出结合起来，是一种较适合本科毕业设计选题系统原型的实现路径。

6.2 不足之处

由于开发周期和实验条件有限，系统仍存在一些不足。首先，题目画像当前已经具备结构化分析形态，但部分逻辑仍以规则和文本信号为主，尚未充分实现稳定的结构化 LLM 输出解析。如果要进一步提升智能化水平，需要增强提示词模板、JSON 输出校验、结果修复和人工确认机制。

【修订建议 07｜不足表述的客观性】“当前已经具备结构化分析形态”略显自我评价式，可改为“题目画像已能够输出关键词、能力要求和风险提示等结构化字段”。这样既具体，也更便于与第 4 章实现内容呼应。

其次，推荐算法仍属于轻量级规则匹配，没有引入更复杂的机器学习模型或历史选题效果反馈。推荐系统研究中的深度学习推荐、矩阵分解、神经协同过滤和词向量语义相似度方法，为后续结合历年选题数据、学生成绩、项目经历和教师评价等信息进一步优化推荐算法提供了参考[11,18,19,22]。

再次，系统的真实用户测试规模有限。虽然系统具备演示账号、运行脚本和自动化测试，但仍需要更多学生和教师参与试用，收集关于推荐准确性、题目画像可读性、页面易用性和任务看板实用性的反馈。

最后，系统在大模型服务接入方面仍需强化生产级能力，例如接口限流、成本控制、敏感信息保护、输出内容审核、失败重试策略和日志追踪等。

6.3 未来展望

后续工作可以从以下几个方向展开。第一，增强题目画像与文档处理的 LLM 编排能力。可以将题目画像生成升级为严格的结构化输出流程，引入 JSON Schema 校验、失败重试、字段缺失补全和人工修订机制，使画像结果更加稳定可信。

第二，优化推荐算法。已有推荐系统研究涉及协同过滤、矩阵分解、神经协同过滤、深度学习推荐和语义向量表示等方向[11,17-19,22]。后续可以在现有规则匹配基础上，引入权重配置、历史反馈、协同过滤或语义向量匹配等方法，并允许教师和学生对推荐结果进行反馈，从而逐步形成更符合实际教学场景的推荐策略。

第三，完善双向选择后的过程质量监控。任务看板可以进一步扩展为进度预警、周报生成、教师反馈记录和材料提交提醒等功能，使系统在完成智能选题和指导关系确认后，继续覆盖毕业设计全过程。

第四，加强系统安全与部署能力。真实上线时需要完善权限审计、数据备份、HTTPS、日志脱敏、访问限流和容器化部署策略，并对大模型调用中的隐私数据进行更严格保护。

第五，扩大用户试用与评估。未来可以邀请更多学生和教师参与试用，从选题耗时、匹配满意度、文档阅读效率、任务完成率和系统易用性等指标评估系统效果，为后续改进提供数据支撑。

综上所述，本文设计并实现的智能化毕业设计选题双向选择系统，在传统毕业设计管理系统的基础上引入题目画像、学生画像、可解释推荐、志愿处理、指导关系确认、异步智能问答、文献处理和任务看板等能力，为毕业设计选题和后续过程推进提供了更具辅助性和智能化的支持。系统达到了预期设计目标，并为后续智慧教学管理系统的进一步研究和应用提供了可参考的工程实践。
