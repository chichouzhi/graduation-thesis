# 毕业设计答辩版文本

## 课题名称

基于大语言模型的智能化毕业设计辅助系统设计与实现

## 一、课题背景与研究意义

毕业设计是本科阶段最重要的综合实践环节之一，覆盖选题、资料检索、方案设计、开发实现、论文撰写和过程检查等多个阶段。传统毕业设计管理系统虽然能够支持课题发布、学生申报、教师审核和过程材料提交，但整体上仍以流程记录和状态流转为主，对学生在“如何理解课题”“如何消化文献”“如何跟踪任务进度”这些核心问题支持不足。

随着大语言模型在自然语言理解、文本生成和上下文问答方面的能力逐步成熟，毕业设计系统已经不应只承担“信息录入平台”的角色，而应进一步向“智能辅助工作台”演进。基于这一判断，本课题以高校毕业设计场景为对象，围绕课题管理、过程管理、智能问答和文档辅助四类能力，设计并实现一套面向毕业设计全过程的智能化辅助系统。

本课题的研究意义主要体现在三个方面。

第一，具有明确的工程实践价值。系统将传统管理流程与异步任务、文档处理和大模型能力结合，能够为学生提供更及时的学术辅助，也有助于教师掌握学生的阶段进度。

第二，具有一定的技术探索价值。课题重点验证了在轻量级 Web 系统中，如何通过“接口契约 + 队列 + Worker + 用例编排层”的方式，将大语言模型安全接入到具体业务场景，而不是简单地把 AI 能力直接拼接到页面上。

第三，具有教育信息化应用价值。系统不仅关注选题阶段的双向选择，还覆盖了聊天问答、文档总结、任务看板等环节，更符合当前高校对全过程管理和个性化支持的实际需求。

## 二、研究现状与问题分析

现有毕业设计管理系统大多采用 B/S 架构，能够较好地完成课题发布、学生申报、教师审核和结果统计等基础业务。从系统建设角度看，前后端分离、角色权限控制和在线流程化管理已经较为成熟。但从用户体验和智能支持角度看，仍存在以下不足。

第一，系统普遍偏重流程管理，轻视学习与研究过程本身。学生在选题理解、资料阅读、问题定位和阶段规划中，仍然主要依赖教师线下指导，系统本身难以提供有效帮助。

第二，现有系统对非结构化文本支持不足。无论是课题描述、学生输入的自然语言问题，还是上传的 PDF 文献，大多只能作为附件保存，缺少进一步分析、摘要和语义处理能力。

第三，很多“智能化”尝试停留在同步接口调用层面，没有解决高耗时模型调用对 Web 请求链路的影响。若直接在接口线程内调用大模型，容易导致响应过慢、错误恢复困难和系统稳定性下降。

基于上述问题，本课题不把重点放在“再做一个普通管理后台”上，而是将研究重点聚焦在三个层面：一是毕业设计场景下的智能辅助能力组织方式，二是大模型接入后的异步运行机制，三是教学业务与 AI 能力之间的边界控制。

## 三、研究目标

本课题的总体目标是设计并实现一套面向毕业设计场景的智能化辅助系统原型，使其既能覆盖基础业务流程，又能展示 AI 在选题辅助、文档处理和过程跟踪中的实际价值。

具体目标如下。

1. 完成后端核心业务能力建设，覆盖身份认证、学期管理、课题管理、志愿填报、任务看板、智能聊天和文档任务等主要模块。
2. 建立统一的接口契约与分层架构，确保业务接口、异步任务状态和错误处理具备一致性与可验证性。
3. 通过消息队列和独立 Worker 进程完成大模型相关任务的异步化，避免在 API 请求线程中同步阻塞调用大模型。
4. 为答辩展示构建清晰的产品主线，即“登录系统、进入工作台、发起聊天、上传文档、查看任务状态、浏览选题与过程管理能力”。
5. 完成独立前端项目的正式设计方案，为后续产品化界面落地提供明确实现依据。

## 四、研究内容与系统设计

### 4.1 系统总体思路

本系统采用前后端分离思路进行设计。后端以 Python Flask 为主体，围绕接口契约、服务层、用例编排层和异步任务层组织代码结构；前端规划为独立的 React + Vite + TypeScript 项目，用于构建适合答辩演示的“AI 学术助手工作台”。

在架构上，系统重点强调两条原则。

第一，所有涉及大模型的主路径必须通过队列和 Worker 执行，API 层只负责请求受理、数据落库和状态查询。

第二，所有与 Prompt、消息组装、文档分块等相关的编排逻辑统一收敛到用例层，避免业务逻辑分散在路由、服务和任务脚本中。

### 4.2 主要功能模块

#### 1. 身份认证与学期管理模块

该模块用于提供基础登录、身份识别和学期上下文能力。系统中的聊天、文档任务、选题和志愿等业务都绑定具体学期，以保证数据边界清晰、管理对象明确。

#### 2. 课题管理与双向选择模块

该模块负责课题录入、课题列表、学生申报、教师确认以及指派关系维护。系统中将 `applications` 作为志愿申报记录，将 `assignments` 作为最终指派真源，并通过对账任务维护选题人数一致性。

这一设计保留了毕业设计“师生互选”的核心业务，同时避免了单纯依赖页面表单和人工统计的低效方式。

#### 3. 智能聊天模块

智能聊天模块是本课题最重要的功能之一。学生可以围绕课题理解、技术方案、论文结构或开发问题发起自然语言提问。系统在受理消息后，不直接在接口线程中调用大模型，而是先创建用户消息和 assistant 占位消息，再将任务入队，由 Worker 异步完成模型调用和结果回写。

这种设计既保证了接口响应速度，也更利于处理失败重试、任务状态追踪和后续扩展。

#### 4. 文档上传与摘要辅助模块

学生可以上传 PDF 文献，由系统进行异步解析和摘要处理。文档任务采用两段式流程：先由 PDF 解析任务提取文本，再由文档任务完成分块处理和总结生成。任务状态统一使用 `pending`、`running`、`done`、`failed` 四态表示，便于前端展示和系统监控。

该模块体现了大语言模型在文献阅读辅助中的实际应用价值，也验证了多阶段异步任务在教学场景中的落地方式。

#### 5. 任务看板与过程管理模块

毕业设计不是一次性提交的结果型任务，而是持续数周甚至数月的过程型任务。为此，系统设计了任务看板与里程碑能力，用于表示不同阶段的计划和执行情况，帮助学生自我管理，也方便教师进行过程督促。

#### 6. 只读推荐与辅助展示模块

系统保留推荐类只读接口，用于对课题进行结构化筛选和展示，但不将推荐逻辑建立在在线大模型重推理之上，而是以已有业务数据和画像结果为基础，控制复杂度与运行成本。

## 五、技术路线与实现方案

### 5.1 后端技术路线

后端采用 Flask 框架实现，核心工作不只是完成接口开发，而是围绕“可维护、可验证、可演示”的目标建立统一工程结构。项目中已经形成了较完整的接口契约文档、架构规格文档和执行计划文档，用于约束接口形状、分层依赖和异步任务行为。

在分层上，系统主要包含以下几层。

1. API 层：负责路由、参数校验、鉴权和序列化。
2. Service 层：负责事务边界、业务入口和入队控制。
3. Use Cases 层：负责聊天组装、文档分块、关键词抽取等编排逻辑。
4. Task 层：负责消息队列消费、状态回写和错误恢复。
5. Adapter 层：负责对接大模型、PDF 解析和外部能力。

这一分层方式的核心价值在于职责清晰，便于测试，也便于通过静态规则和集成测试验证架构是否被正确执行。

### 5.2 异步任务技术路线

系统中所有涉及大模型的能力均采用“受理请求 + 创建任务 + 异步执行 + 状态轮询”的模式实现。聊天消息、文档摘要和课题关键词抽取均通过队列与 Worker 运行，不在 API 进程中同步阻塞执行。

这样做主要解决了三个问题。

1. 避免长耗时模型调用拖慢接口响应。
2. 便于统一处理限流、失败补偿和状态追踪。
3. 使系统演示更具产品感，能够体现任务流转过程，而不是静态结果页面。

### 5.3 前端技术路线

当前项目前端采用新的独立化方案进行规划，即在仓库根目录下新增 `frontend/` 项目，技术栈拟采用 React、Vite、TypeScript、React Router、Tailwind CSS、shadcn/ui、TanStack Query、Zustand 和 Axios。

前端定位不是传统教务后台，而是“AI 学术助手工作台”。其主演示链路将围绕登录、工作台首页、智能聊天、文档任务、课题浏览和任务看板展开。该方案已经形成正式设计文档，后续可据此进入具体实现阶段。

## 六、已完成成果

结合当前项目进展，本课题已完成的主要成果包括以下几个方面。

1. 已建立较完整的后端规范体系，包括接口契约、架构规格和任务执行文档。
2. 已完成后端核心分层结构建设，并围绕聊天、文档、课题和双向选择等核心业务建立了清晰的领域边界。
3. 已完成基于队列和 Worker 的异步任务运行主线设计，并对聊天任务、文档任务、关键词任务和对账任务给出统一约束。
4. 已完成身份、学期、选题、志愿、任务看板等支撑性业务的后端接口规划与实现基础。
5. 已形成独立前端项目的正式产品化设计文档，明确了答辩演示所需的页面优先级和交互主线。

需要说明的是，当前阶段的交付重点在后端能力、接口契约和异步运行机制上；前端产品化界面已完成正式设计，但仍处于待实现状态。因此，本课题在答辩中应如实表述为“后端核心能力已完成，前端已完成独立设计并可按既定方案继续落地”，而不应表述为“前后端全部完成并已全面联调上线”。

## 七、创新点与特色

本课题的特色不在于简单调用某个大模型接口，而在于将大模型能力纳入毕业设计业务场景中，并通过工程化手段使其具备可运行、可管理和可验证的特征。

主要体现在以下几个方面。

1. 将毕业设计系统从流程管理工具扩展为智能辅助工作台，覆盖聊天问答、文档摘要和过程跟踪等实际使用场景。
2. 采用“API 不直连 LLM、LLM 主路径全部异步化”的工程策略，保证了系统响应速度与架构稳定性。
3. 将 Prompt 组装、历史裁剪、文档分块等复杂逻辑收敛到用例层，提升了代码边界清晰度和后续维护性。
4. 将选题业务、过程管理和 AI 辅助能力统一到同一个毕业设计场景中，增强了系统整体性与展示价值。

## 八、不足与后续改进方向

虽然系统已经形成较清晰的后端主线和前端设计方案，但仍存在一些可继续完善的方面。

第一，当前前端产品化界面尚未正式落地，后续需要按既定设计方案完成 `frontend/` 项目开发，并与现有后端接口完成联调。

第二，大模型能力目前主要聚焦于聊天与文档摘要，后续可以进一步扩展到课题理解辅助、论文结构建议、阶段总结生成等更细化场景。

第三，推荐能力当前以只读筛选和画像结果利用为主，后续可以在不破坏系统稳定性的前提下，探索更合理的推荐策略和评价机制。

## 九、结论

本课题围绕高校毕业设计全过程中的“选题难、过程跟踪弱、文档理解成本高、智能支持不足”等问题，设计了一套基于大语言模型的智能化毕业设计辅助系统。项目以 Flask 后端为基础，强调接口契约、分层边界和异步任务机制，在系统架构上避免了将大模型直接堆叠到传统管理后台中的常见做法。

从当前完成情况看，系统已经形成较完整的后端核心能力和答辩演示主线，并完成了独立前端项目的正式设计方案。整体上，本课题较好地实现了“毕业设计管理”与“AI 辅助能力”相结合的目标，具有较强的工程实践意义和进一步扩展价值。
