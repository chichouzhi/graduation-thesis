# 前端当前已完成功能梳理

## 文档目的

本文档用于说明截至目前，毕业设计项目中 `frontend/` 独立前端工程已经完成的功能、真实联调范围、当前仍为静态骨架的页面，以及建议的下一步推进方向。

项目定位是“AI 学术助手工作台”，强调学生端、学术生产力、异步任务可视化和适合答辩演示的工作台体验，而不是通用后台模板。

## 当前前端工程状态

前端已经在 `frontend/` 下独立建立完成，技术栈已落地：

- React
- Vite
- TypeScript
- React Router
- Tailwind CSS
- shadcn/ui
- TanStack Query
- Zustand
- Axios

工程目录已经形成清晰分层，核心目录包括：

- `src/app`
- `src/pages`
- `src/components`
- `src/features`
- `src/lib`
- `src/routes`

## 当前已建立的页面路由

当前已可访问的页面包括：

- `/login`
- `/app/dashboard`
- `/app/chat`
- `/app/documents`
- `/app/topics`
- `/app/taskboard`

其中 `/login` 为登录入口，`/app/*` 页面均通过受保护布局承接应用壳。

## 应用壳完成情况

应用壳已经实现并可正常运行，包含：

- 左侧导航栏
- 顶部栏
- 主内容区
- 受保护路由布局

视觉上已经形成“浅色、理性、干净但有层次”的工作台风格，整体更接近学生端学术产品，而不是通用管理后台。

## 已完成的真实联调功能

### 1. 登录链路

`/login` 已接入真实后端登录接口：

- 调用 `POST /api/v1/auth/login`
- 成功后写入本地会话信息
- 保存 `access_token`
- 登录成功后进入 `/app/dashboard`
- 已统一适配 `ErrorEnvelope`

登录状态通过 Zustand 管理，持久化通过本地存储实现。

### 2. Chat 页面真实联调

`/app/chat` 已不是静态页面，而是完成了真实聊天主链路联调。

已接入能力包括：

- 读取会话列表
- 默认创建通用学术咨询会话
- 读取消息列表
- 发送用户消息
- 接收后端返回的 `job_id`
- 根据 `job_id` 轮询 chat job 状态
- 按 `pending / running / done / failed` 状态驱动停止轮询
- 展示 assistant 占位消息和最终消息
- 展示最近任务状态与错误信息

这一页已经具备答辩时演示“异步 AI 对话链路”的能力。

### 3. Documents 页面真实联调

`/app/documents` 已完成真实文档任务主链路联调。

已接入能力包括：

- 上传 PDF
- 选择任务类型
- 选择输出语言
- 拉取文档任务列表
- 拉取单任务详情
- 根据任务状态轮询详情
- 列表与详情联动
- 上传成功后自动选中新任务
- `pending / running / done / failed` 状态展示
- `done` 时展示摘要结果与 bullet points
- `failed` 时展示错误类型与错误信息
- 统一适配 `ErrorEnvelope`

这一页已经具备答辩时演示“异步文档处理链路”的能力。

### 4. Topics 页面真实联调

`/app/topics` 已从本地 mock 页面升级为真实题目浏览页。

已接入能力包括：

- 按当前学期拉取题目列表
- 拉取单个题目详情
- 左侧列表与右侧详情联动
- 默认选中首条题目
- 点击不同题目后切换详情
- 展示题目状态、摘要、研究要求、技术关键词、系统抽取关键词、容量、教师 ID、学期 ID、更新时间
- 统一适配 `ErrorEnvelope`

当前 `Topics` 的浏览主链路仍是“题目列表 + 详情”，同时前端新增了“老师分析 + 学生推荐”的演示流程，暂未接入真实志愿提交和推荐后端接口。

在此基础上，前端又补了一层“老师分析 + 学生推荐”的产品化演示流程：

- 老师可以录入或导入题目，生成结构化分析摘要、适合学生类型和风险提示
- 学生可以输入兴趣、技能、目标和每周投入时间，得到前端侧的推荐试算结果
- 当前这部分仍是前端演示逻辑，后续可直接替换成真实大模型分析接口和推荐接口

### 5. 受保护布局稳定性修复

在真实联调过程中，曾发现登录后进入应用壳时会触发 React 无限更新问题。

已完成修复内容包括：

- 修复 `ProtectedLayout` 中的 Zustand selector 导致的重复渲染问题
- 新增回归测试，防止再次出现相同问题

因此当前登录后进入 `/app/*` 的应用壳链路已经稳定。

`/app/dashboard` 当前仍以静态假数据为主，已完成的是：

- 首页工作台概览布局
- 近期工作展示
- 异步任务状态总览

- 最近活动

### 2. Taskboard

`/app/taskboard` 当前仍是静态骨架页，已完成的是：

- 阶段列式布局
- 开题、实现、论文、答辩准备等节奏展示
- 基于 mock 数据的任务卡片展示

目前还没有接入真实任务看板接口。

## 已完成的数据层与工程能力

为了支持后续继续扩展，前端已经具备较完整的基础能力：

- Axios 统一请求封装
- 登录态自动附带 Bearer Token

- `ErrorEnvelope` 统一错误适配

- 针对异步任务的状态驱动轮询模式

目前 `chat`、`documents`、`topics` 三个模块都已经形成了较清晰的 feature 分层。

## 当前实现边界总结

如果从“答辩可演示”的角度来看，当前前端已经具备三条较有说服力的主链路：

1. 登录进入学生端工作台
2. Chat 异步对话主链路
3. Documents 异步文档处理主链路
4. Topics 真实题目浏览主链路
5. Topics 老师分析与学生推荐演示链路

其中：

- Chat 展示“异步 AI 回复”
- Documents 展示“异步 PDF 处理”
- Topics 展示“真实选题浏览”

这三者已经足以支撑一个较完整的“AI 学术助手工作台”产品演示主线。

## 建议的下一步优先级

建议后续优先顺序如下：

1. 接入 `Taskboard` 真实数据，使工作台形成“聊天 + 文档 + 选题 + 任务推进”的完整闭环
2. 补齐 `Topics` 的志愿提交或“我的志愿状态”链路
3. 视答辩重点，再决定是否接入推荐题目能力
4. 最后再考虑 Dashboard 的真实统计聚合

## 一句话总结

截至目前，前端已经从“独立工程与静态骨架”推进到“登录、Chat、Documents、Topics 多页面真实联调可演示”的阶段，已经具备较强的答辩展示基础，剩余工作重点转向 `Taskboard`、`Topics` 深化和工作台完整闭环。
