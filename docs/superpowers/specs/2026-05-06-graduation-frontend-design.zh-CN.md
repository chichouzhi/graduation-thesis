# 毕业设计前端设计文档

## 背景

当前仓库已经包含 Flask 后端、基于队列的异步任务流程、位于 `spec/contract.yaml` 的接口契约，以及较完整的后端测试覆盖，但还没有独立的前端项目。

现阶段后端最有产品展示价值的能力主要集中在以下几个方面：

1. 异步聊天请求受理与任务状态轮询。
2. 异步 PDF 上传、解析与文档总结任务流程。
3. 选题、任务看板、身份与学期等支撑性业务页面。

对于毕业设计交付而言，前端不需要平均覆盖后端全部能力，而是需要支撑一条清晰、有说服力的答辩演示主线：用户可以登录、完成核心交互、观察异步处理过程，并感受到这个系统不是简单的静态 CRUD 页面集合。

## 目标

在仓库根目录下创建独立前端项目 `frontend/`，作为一套适合毕业答辩演示的产品化前端。

这套前端应当满足：

- 优先展示后端最强的核心能力。
- 优先保证视觉完成度和演示流畅性，而不是追求全量功能覆盖。
- 主演示链路支持真实 API 联调。
- 次要模块允许部分联调、部分静态展示。
- 与现有 Python 后端项目结构隔离。

## 非目标

- 不在第一阶段构建覆盖所有后端域能力的完整生产级管理后台。
- 不将当前项目重构为复杂的 monorepo 工程体系。
- 不引入 SSR、微前端或多应用拆分。
- 不在第一轮前端实现中覆盖所有教师端、管理员端流程。
- 不替换现有后端契约与分层模型。

## 推荐方案

采用独立前端项目 `frontend/`，技术栈建议为：

- React
- Vite
- TypeScript
- React Router
- Tailwind CSS
- shadcn/ui
- TanStack Query
- Zustand
- Axios

这是最适合毕业答辩版前端的平衡方案：

- 搭建速度快，便于快速迭代。
- 容易做出较好的视觉完成度。
- 与当前后端接口对接简单。
- 相比 Next.js 或重型企业级前端方案，实施风险更低。

## 产品定位

前端整体应当被定位为一个“AI 学术助手工作台”，而不是普通管理系统。

这意味着：

- 首页应突出活动、任务和结果，而不是纯列表页。
- 聊天与文档流程应成为最核心的用户故事。
- 选题与任务看板作为辅助模块，用来证明系统覆盖范围与业务完整性。

答辩演示时，产品故事建议按以下方式展开：

1. 用户登录系统。
2. 用户进入工作台首页，看到近期工作概览。
3. 用户使用异步聊天，看到基于任务的状态变化。
4. 用户上传 PDF，看到文档任务推进和总结结果。
5. 用户进一步查看选题页与任务看板页，证明系统不仅有 AI 能力，也覆盖毕业过程管理。

## 目录结构

前端项目应独立创建在：

```text
frontend/
```

推荐仓库结构如下：

```text
app/                 # Flask 后端
docs/
spec/
tests/
frontend/            # 新建 React 前端
```

采用这种结构的原因：

- Python 与 Node.js 的依赖体系相互独立。
- 答辩时更容易向老师说明“前后端分离”的项目结构。
- 避免前端构建产物污染后端源代码目录。
- 不破坏当前后端仓库既有结构。

## 页面优先级

### P0：主演示链路

以下页面必须优先实现，并达到较高完成度。

#### `/login`

职责：

- 接收用户名和密码。
- 通过后端接口完成认证。
- 为后续请求保存登录状态。
- 登录成功后跳转到应用工作台。

价值：

- 建立完整产品入口。
- 让后续演示显得是同一套系统，而不是多个独立页面拼接。

#### `/app/dashboard`

职责：

- 展示当前用户和当前学期上下文。
- 展示最近聊天任务与最近文档任务。
- 展示核心统计卡片，如聊天数、文档任务数、完成数、失败数。
- 提供跳转到聊天、文档、选题、任务看板的快捷入口。

价值：

- 作为答辩演示的起点页非常合适。
- 帮助讲清系统是统一工作台而不是零散功能集合。

#### `/app/chat`

职责：

- 展示会话列表。
- 展示当前会话消息流。
- 支持发送用户消息。
- 显示异步任务状态，如 `pending`、`running`、`done`、`failed`。
- 轮询聊天任务状态，并在完成后更新 assistant 消息内容。

价值：

- 这是当前后端最强的产品能力之一。
- 能直接展示队列驱动的异步交互特性。

#### `/app/documents`

职责：

- 上传 PDF 文档。
- 展示文档任务列表。
- 展示任务状态、进度和总结结果。
- 支持查看单个任务的详情。
- 反映异步文档处理阶段与最终结果。

价值：

- 这是当前后端另一条最强主线能力。
- 能展示文档摄取、异步处理与结果呈现的完整闭环。

### P1：辅助展示页面

以下页面应在主演示链路稳定后完成。

#### `/app/topics`

职责：

- 展示题目列表与题目详情。
- 展示志愿/申请状态（如有）。
- 强调系统不仅有 AI 助手，还覆盖毕业选题场景。

该页面可以部分联调、部分静态展示。

#### `/app/taskboard`

职责：

- 展示里程碑或任务进度。
- 提供进度视图或时间线视图。
- 证明系统支持结构化的毕业过程管理。

该页面也允许部分联调、部分静态展示。

### P2：可选或延后项

- 个人中心/设置
- 完整教师端与管理员端流程
- 复杂筛选、报表
- 主演示链路之外的复杂编辑能力

## 信息架构

推荐路由结构如下：

```text
/login
/app
/app/dashboard
/app/chat
/app/documents
/app/topics
/app/taskboard
```

推荐整体布局：

- 左侧导航栏承载主模块切换。
- 顶部栏承载用户、学期上下文与快捷操作。
- 主内容区展示具体页面内容。

推荐导航顺序：

1. Dashboard
2. Chat
3. Documents
4. Topics
5. Taskboard

这个顺序不是按后端域划分，而是按答辩展示优先级排序。

## 界面风格方向

界面应当具有明确的产品感和展示感，而不是普通后台模板。

推荐方向：

- 清晰的工作台布局。
- 首页统计卡片有明显层级。
- 以浅色主题为主。
- 强调偏学术、偏生产力的配色，而不是过于娱乐化。
- 仅在异步状态变化等关键位置使用有限动效。

重点视觉应聚焦在：

- 异步任务状态标签。
- 最近活动和近期结果概览。
- 聊天消息流。
- 文档结果卡片与任务进度。

应避免：

- 以表格为主、过于企业后台化的整体观感。
- 过暗、过于霓虹或科幻风格。
- 在应用工作台内部使用类似官网 landing page 的夸张 hero 区域。

## 数据与状态策略

### 服务端状态

TanStack Query 用于管理：

- 认证后的资源加载。
- 会话列表。
- 聊天任务轮询。
- 文档任务轮询。
- 基于服务端资源派生的首页统计数据。

轮询行为应明确：

- 当 chat job 或 document task 处于 `pending` 或 `running` 时开始轮询。
- 到达终态后停止轮询。
- 失败状态必须明确反馈给用户。

### 客户端状态

Zustand 只用于少量全局状态：

- 登录态摘要。
- 当前用户信息摘要。
- 当前学期选择（如需要）。
- 不适合放在局部组件中的轻量 UI 状态。

不要用 Zustand 替代服务端状态管理。

## API 对接顺序

### 第一阶段：主演示链路接口

优先接入：

- `POST /auth/login`
- `GET /conversations`
- `POST /conversations/{conversation_id}/messages`
- `GET /chat/jobs/{job_id}`
- `POST /document-tasks`
- `GET /document-tasks`
- `GET /document-tasks/{task_id}`

### 第二阶段：辅助模块接口

后续再接入：

- 选题相关接口
- 任务看板相关接口

如果部分辅助接口当前价值不高或后端仍需补充，这些页面可以先使用静态或半静态展示，只要主演示链路是真实联调即可。

## 错误处理

前端应统一适配后端的 `ErrorEnvelope` 错误格式。

建议使用一个共享的 API 错误适配层处理：

- `UNAUTHORIZED`
- `VALIDATION_ERROR`
- `NOT_FOUND`
- `QUEUE_UNAVAILABLE`
- `DOMAIN_ERROR`
- 契约中定义的其他错误码

行为要求：

- 表单级错误贴近输入项显示。
- 页面级拉取失败展示可重试的错误区块。
- 异步任务失败必须在聊天/文档 UI 内可见，而不是静默消失。

## 答辩演示流程

推荐答辩演示路径：

1. 登录。
2. 进入工作台首页。
3. 打开聊天页，发送消息，讲解异步任务状态变化。
4. 打开文档页，上传 PDF，讲解任务进度与结果展示。
5. 简短展示选题页。
6. 简短展示任务看板页。

这种顺序能先把最强的技术价值讲出来，再用辅助页面补充系统广度。

## Vibing Code 开发流程

这里的“vibing code”不应理解为无序地让 AI 一次性生成所有前端，而应理解为分轮次、分层次、逐步收敛的 AI 协作开发流程。

### Round 1：搭建项目骨架与应用壳

交付物：

- `frontend/` 项目初始化
- 路由系统
- 应用壳布局
- dashboard/chat/documents/topics/taskboard 的静态骨架页

要求：

- 先使用假数据
- 暂不接真实接口
- 只聚焦结构、路由和导航

### Round 2：提升视觉完成度

交付物：

- 更完善的页面布局
- 首页卡片层级优化
- 聊天页与文档页的视觉强化
- 空状态、加载 skeleton、状态标签

要求：

- 保持已有结构稳定
- 优先提升“产品感”和答辩展示效果

### Round 3：接入主演示链路 API

交付物：

- 登录联调
- 聊天联调
- 文档联调
- Axios API client
- TanStack Query hooks

要求：

- 只接主演示链路
- 不要同时扩散到次要模块

### Round 4：补齐异步状态体验

交付物：

- chat job 轮询
- document task 轮询
- chat/documents/dashboard 的终态刷新
- 明确的失败态 UI

要求：

- 轮询要有限、受状态驱动
- 不要依赖隐式刷新

### Round 5：答辩优化

交付物：

- 更适合演示的文案
- 更强的首页信息表达
- 一致的成功/失败/空态反馈
- 轻量动效
- 更适合答辩截图与演示的默认状态

要求：

- 不在这一轮做大规模架构调整
- 这一轮只服务于演示质量提升

## 面向 AI 的提示词使用原则

每一轮提示词都只要求 AI 完成一层工作，而不是把所有事情混在一起。

合理的提示方式：

- 搭建项目与路由壳子
- 优化 dashboard/chat/documents 的视觉效果，但不接接口
- 只接登录、聊天、文档接口
- 只补异步轮询与状态反馈
- 只做答辩演示优化

不合理的提示方式：

- 一次性要求 AI 完成全部前端、全部接口、全部视觉和全部优化

核心原则是：

**一轮只做一类事情**

只有这样，AI 产出才容易审核、容易修正、容易持续推进。

## 风险

### 风险一：次要模块投入过多

如果把 topics/taskboard 和 chat/documents 放在同等优先级，前端很容易“看起来覆盖很广，但每个点都不够强”。

缓解方式：

- 锁定 dashboard、chat、documents 为主范围。

### 风险二：先做视觉、后补结构导致返工

如果在整体布局和路由结构没有稳定前就深做样式，后续返工成本会很高。

缓解方式：

- 明确分开 Round 1 与 Round 2。

### 风险三：异步体验在前端不可见

如果 chat/document 的 `pending/running/done/failed` 状态没有清晰体现在 UI 中，那后端最有价值的工作会在答辩时“看不出来”。

缓解方式：

- 在聊天与文档页面显式设计状态反馈。

### 风险四：前后端术语漂移

如果前端页面与 API 层命名偏离 `spec/contract.yaml`，联调和答辩讲解都会更困难。

缓解方式：

- API 层代码优先使用契约字段名和后端资源命名。

## 最终建议

应当基于 `frontend/` 创建一套独立的前端项目，并把它定位为“AI 学术助手工作台”。

这套前端应当：

- 以 dashboard、chat、documents 为核心
- 在主演示链路上完成真实后端联调
- 用 topics 和 taskboard 证明系统业务广度
- 用分轮次、分层次的 AI 协作流程推进，而不是一口气生成全部内容

这是当前最适合你这个毕业设计的前端建设路径，也是最有利于答辩展示的方案。
